## 一、热点课程抢课（最难的综合场景）

### 问题描述

开学选课季，某门「网红选修课」（如《Python 数据分析》）只有 **50 个名额**，却有 **5000 名学生**卡在选课开始的那一秒同时点击选课。瞬时 QPS 从日常的几十飙到上万，出现三个必须同时解决的难题：

1. **容量超卖**：50 个名额被 60 个人抢到（多个线程同时读到「余量 = 1」）。
2. **重复选课**：学生手抖点两次、网络重试、MQ 重复消费，导致同一人占两个名额。
3. **课程时间冲突**：学生抢到了这门课，但没发现它和自己已选的另一门课时间重叠。
4. **热点缓存击穿**：热门课程的「余量」缓存 key 过期瞬间，上万个请求同时打到数据库，把连接池打满。

**面试官追问点**：这是一个把「缓存三兄弟 + 分布式锁 + Redis 原子扣减 + 幂等 + 冲突检测 + MQ 削峰」全部串起来的综合题，考察你能否**分层设计 + 权衡取舍**，而不是只会背单个知识点。

### 完美解决方案

#### 第 1 步：缓存预热 + 热点课程缓存永不过期

```java
// 选课开始前，把热门课程余量预加载到 Redis（避免第一波请求直接打 DB）
// 热点课程设置"逻辑不过期"，物理不设 TTL，防止击穿
redis.set("course:stock:" + courseId, String.valueOf(50));
```

#### 第 2 步：Redis 原子扣减 + 判重 + 冲突检测（Lua 一次搞定）

```lua
-- 选课核心 Lua 脚本：把「查余量 + 判重 + 查时间冲突 + 扣减」合并为一次原子操作
-- KEYS[1] = 课程余量 key        course:stock:1001
-- KEYS[2] = 学生已选课程集合     student:courses:2024001
-- KEYS[3] = 课程时间槽集合       course:timeslot:1001   (存周几第几节，如 "Mon-3-4")
-- ARGV[1] = 学生ID  ARGV[2] = 课程ID  ARGV[3] = 本课程时间槽  ARGV[4] = 可选时间槽集合
local stock = redis.call('GET', KEYS[1])
if not stock or tonumber(stock) <= 0 then
    return -1   -- 名额已满
end
-- 判重：该学生是否已选过这门课
if redis.call('SISMEMBER', KEYS[2], ARGV[2]) == 1 then
    return -2   -- 重复选课
end
-- 冲突检测：本课程时间槽是否与学生已选其他课程的时间槽重叠
local conflicts = redis.call('SINTER', KEYS[3], KEYS[4])
if #conflicts > 0 then
    return -3   -- 时间冲突
end
-- 全部通过，扣减余量 + 记录选课
redis.call('DECRBY', KEYS[1], 1)
redis.call('SADD', KEYS[2], ARGV[2])
redis.call('SADD', KEYS[4], ARGV[3])   -- 把本课程时间槽并入学生已占用集合
return 1        -- 选课成功
```

> **为什么用 Lua**：Redis 单线程执行 Lua，脚本内多个命令天然原子，避免「先查后改」的竞态窗口；同时减少网络往返次数（原本要 4 次 Redis 调用，现在 1 次）。

```java
// Java 调用
Long result = redis.execute(script,
    List.of("course:stock:1001", "student:courses:2024001", "course:timeslot:1001", "student:timeslots:2024001"),
    studentId, String.valueOf(courseId), "Mon-3-4");
switch (result.intValue()) {
    case -1: throw new BizException("名额已满");
    case -2: throw new BizException("请勿重复选课");
    case -3: throw new BizException("与已选课程时间冲突");
    default: /* 成功，进入异步落库 */ break;
}
```

#### 第 3 步：数据库兜底（唯一索引 + 条件更新 + 冲突校验）

```sql
-- ① 选课记录表：复合唯一索引 (student_id, course_id) 防止重复选课
CREATE TABLE enrollment (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    student_id BIGINT NOT NULL,
    course_id BIGINT NOT NULL,
    semester VARCHAR(20) NOT NULL,
    status TINYINT DEFAULT 0,            -- 0待确认 1已选 2已退
    UNIQUE KEY uk_student_course (student_id, course_id),
    KEY idx_course (course_id)
);

-- ② 课程容量条件更新：capacity > 0 才扣，天然防超卖
UPDATE course SET capacity = capacity - 1 WHERE id = ? AND capacity > 0;

-- ③ 时间冲突在 DB 层再校验一次（Redis 可能丢数据，DB 是最终防线）
-- 查该学生已选课程的时间槽，与本课程比对，冲突则回滚
```

#### 第 4 步：MQ 异步削峰 + 幂等消费

```
Redis 扣减成功 → 发送 MQ（选课消息）
  → 选课服务异步消费 → 写 enrollment 表 → 扣 DB 容量
    → 失败重试（幂等，重复消费直接跳过）
```

```java
// 消费者按 (studentId + courseId) 做幂等，防 MQ 重复投递导致重复选课
public void onEnrollMessage(EnrollMsg msg) {
    boolean first = redis.setIfAbsent("enroll:dedup:" + msg.getStudentId() + ":" + msg.getCourseId(),
            "1", 1, TimeUnit.HOURS);
    if (!first) return;   // 已处理过，忽略
    try {
        enrollmentService.doEnroll(msg);   // 落库 + 扣容量（DB 唯一索引兜底）
    } catch (DuplicateKeyException e) {
        // 唯一索引兜底，重复插入说明已选，忽略即可
    }
}
```

#### 分层总结

```
前端防重(按钮置灰/验证码) → 网关限流(令牌桶) → 服务端限流(Sentinel)
  → Redis Lua 原子扣减(防超卖/防重/防冲突) → MQ 异步削峰 → DB 唯一索引+条件更新兜底
```

> **权衡**：Redis 扣减性能极高（可达数万 QPS），但 Redis 与 DB 存在短暂不一致，靠 MQ 保证最终一致 + 定时对账修复。热点课程「逻辑不过期」牺牲了一点实时性，换来不击穿。

## 二、选课并发冲突检测（时间冲突 + 容量超卖）

### 问题描述

学生 A 同时（并发）提交两门「时间重叠」的课程，或同一个学生用两个设备同时选同一门课。系统需要在并发下保证：

1. **时间不冲突**：一个学生在同一时间段（如周一第 3-4 节）只能选一门课。
2. **不超卖**：课程容量扣减不出现负数。
3. **不重复**：同一门课不能选两次。

**难点**：「先查后写」存在竞态窗口 —— 两个请求都先查「时间是否冲突」，都发现没冲突，然后同时写入，最终学生 A 的课表里出现两门时间重叠的课。

**面试官追问点**：你会用什么机制保证并发下的冲突检测正确？唯一索引够不够？锁的粒度怎么选？

### 完美解决方案

#### 方案一：唯一索引（防重复，最简单可靠）

```sql
-- 复合唯一索引直接防重复选课（同一学生同一课程只能一条记录）
UNIQUE KEY uk_student_course (student_id, course_id);
```

> 唯一索引只能防「同一门课重复选」，**防不了「时间冲突」**（因为时间冲突是两门不同课程，记录不同，唯一索引拦不住）。时间冲突需要额外的业务约束。

#### 方案二：时间槽唯一索引（把冲突检测下沉到数据库）

把「学生 + 时间段」作为唯一键，冲突检测变成唯一索引约束：

```sql
-- 学生时间占用表：一个学生同一时间段只能占一条记录
CREATE TABLE student_timeslot (
    student_id BIGINT NOT NULL,
    semester VARCHAR(20) NOT NULL,
    day_of_week TINYINT NOT NULL,        -- 周几 1-7
    period TINYINT NOT NULL,             -- 第几节 1-12
    course_id BIGINT NOT NULL,
    UNIQUE KEY uk_student_slot (student_id, semester, day_of_week, period)
);
```

```java
// 选课时插入时间占用记录，若时间冲突会抛 DuplicateKeyException
try {
    timeslotMapper.insert(new Timeslot(studentId, semester, dayOfWeek, period, courseId));
} catch (DuplicateKeyException e) {
    throw new BizException("与已选课程时间冲突");
}
```

> **原理**：把「业务规则校验」转化为「数据库唯一约束」，数据库在并发下天然保证不冲突，无需加锁。这是最优雅的方案。

#### 方案三：悲观锁（对冲突检测 + 扣减加锁）

```sql
-- 悲观锁：选课前先锁住该学生的选课状态行，串行化同一学生的选课操作
SELECT * FROM student WHERE id = ? FOR UPDATE;
-- 然后再做冲突检测 + 扣减 + 写入，事务提交释放锁
```

```java
@Transactional
public void enroll(Long studentId, Long courseId) {
    // 1. 行锁：同一学生的选课操作串行化，杜绝并发冲突
    Student student = studentMapper.selectForUpdate(studentId);
    // 2. 检测时间冲突
    checkTimeConflict(studentId, courseId);
    // 3. 扣容量 + 写记录
    courseMapper.deductCapacity(courseId);
    enrollmentMapper.insert(studentId, courseId);
}
```

#### 方案对比与权衡

| 方案 | 优点 | 缺点 | 适用 |
|------|------|------|------|
| 复合唯一索引（student+course） | 简单，防重复 | 防不了时间冲突 | 防重复选课 |
| 时间槽唯一索引 | 冲突检测下沉 DB，无锁，并发高 | 需额外建表/维护占用记录 | 时间冲突检测 |
| 悲观锁 | 逻辑清晰，强一致 | 锁粒度大，并发低，可能死锁 | 低频操作（退课/调课） |
| Lua 原子脚本 | 一次原子完成，性能最好 | 逻辑在 Redis，需保证与 DB 一致 | 高并发抢课 |

> **最佳实践**：高并发抢课用 **Lua 原子脚本（Redis）** 做前置拦截 + **时间槽唯一索引（DB）** 做最终兜底，两者结合。

## 三、教务系统慢 SQL 专项（GPA / 排名 / 搜索 / 课表）

### 问题描述

教务系统里有几类典型慢 SQL，数据量大（几十万学生 × 几千课程 × 数百万选课记录）时尤为突出：

1. **GPA / 学分绩点统计**：聚合多表、大数据量 `GROUP BY`。
2. **成绩排名**：全校/全院成绩排名，需要深分页 + 排序。
3. **课程模糊搜索**：`LIKE '%课程名%'` 导致索引失效。
4. **学生课表查询**：按学期 + 学号联表查课表，缺少索引。

**面试官追问点**：能否针对每个场景说出「为什么会慢 → 怎么定位 → 怎么优化」。

### 完美解决方案

#### 场景 1：GPA / 学分绩点统计

```sql
-- ❌ 慢：实时聚合所有选课记录算 GPA，每次全表扫
SELECT student_id, SUM(grade * credit) / SUM(credit) AS gpa
FROM enrollment e
JOIN course c ON e.course_id = c.id
GROUP BY student_id;
```

**优化**：
- **预计算 + 冗余**：选课/成绩确定后，把 GPA、总学分**预计算并落库**到学生表，查询直接读冗余字段，不做实时聚合。
- **异步更新**：成绩发布后通过 MQ 异步重算该学生 GPA，而非每次查询实时算。
- **只给必要字段建索引**：`enrollment(student_id)`、`enrollment(course_id)` 建索引加速 JOIN。
- **数据量极大**时可考虑**并行查询**或**离线数仓**（统计类报表不查业务库）。

#### 场景 2：成绩排名（深分页）

```sql
-- ❌ 深分页：OFFSET 100000 会先扫 10 万行再丢弃
SELECT * FROM score ORDER BY total_score DESC LIMIT 100000, 20;

-- ✅ 方案一：覆盖索引 + 延迟关联
SELECT s.* FROM score s
INNER JOIN (SELECT student_id FROM score ORDER BY total_score DESC LIMIT 100000, 20) t
ON s.student_id = t.student_id;

-- ✅ 方案二：游标分页（记录上一页最后一条的排名分数和 ID）
SELECT * FROM score
WHERE (total_score < ? OR (total_score = ? AND student_id > ?))
ORDER BY total_score DESC, student_id ASC
LIMIT 20;
```

> 排名场景推荐**游标分页**（学生翻页不可能跳页，顺序翻最合适）；若必须跳页，用覆盖索引 + 延迟关联。

#### 场景 3：课程模糊搜索（LIKE 索引失效 → ES）

```sql
-- ❌ 左模糊导致索引失效，课程表数据量大时全表扫
SELECT * FROM course WHERE course_name LIKE '%数据分析%';
```

**优化**：
- 前缀能确定时用右模糊 `LIKE '数据分析%'`（走索引）。
- 真正需要全文检索（课程名、教师名、简介关键词）时，把课程数据**同步到 Elasticsearch**，用 ES 的分词 + 倒排索引做搜索，MySQL 只做精确查询。
- 同步方式：canal 监听 binlog → 投递 MQ → 更新 ES（见第六节）。

#### 场景 4：学生课表查询（索引设计）

```sql
-- ❌ 缺少索引，按学期+学号查课表全表扫
SELECT e.*, c.course_name, c.teacher_id, c.day_of_week, c.period
FROM enrollment e
JOIN course c ON e.course_id = c.id
WHERE e.student_id = ? AND e.semester = ?;
```

**优化**：
- `enrollment` 建联合索引 `(student_id, semester)`，遵循最左前缀。
- `course` 表主键/`id` 本身有索引，JOIN 走索引。
- 避免 `SELECT *`，只查课表展示需要的列，必要时用覆盖索引。

#### 通用排查流程（教务版）

1. 开慢查询日志，定位慢 SQL。
2. `EXPLAIN` 看 `type`（是否为 `ALL`）、`key`（是否命中）、`Extra`（是否 `Using filesort`/`Using temporary`）。
3. 对应优化：补索引 → 覆盖索引 → 预计算冗余 → 分库分表 → 迁 ES。

## 四、分布式事务：选课 = 扣容量 + 写记录 + 更新学分

### 问题描述

选课是一个跨表/跨服务的操作，需要同时完成三件事：

1. **课程服务**：课程容量 `capacity - 1`。
2. **选课服务**：插入选课记录 `enrollment`。
3. **学生服务**：更新学生已选学分 `credit + 课程学分`。

如果「扣了容量」但「选课记录没写成」，会出现容量少了但学生没选上；反之「写了记录」但「学分没加」，学生毕业学分对不上。需要保证三者**要么全成功，要么全回滚**。

**面试官追问点**：单体用本地事务能解决吗？拆成微服务后怎么办？强一致和最终一致怎么选？

### 完美解决方案

#### 方案一：单体 / 单库 → 本地事务（最简单）

```java
// 单体应用，三个表在同一数据库，用 @Transactional 本地事务即可保证一致性
@Transactional(rollbackFor = Exception.class)
public void enroll(Long studentId, Long courseId) {
    courseMapper.deductCapacity(courseId);          // 扣容量
    enrollmentMapper.insert(studentId, courseId);    // 写选课记录
    studentMapper.addCredit(studentId, courseCredit); // 加学分
}
```

#### 方案二：微服务 → MQ 最终一致性（高频答案）

```java
// 选课服务：本地事务保证「扣容量 + 写记录」原子，同时发半消息
@Transactional
public void enroll(Long studentId, Long courseId) {
    courseMapper.deductCapacity(courseId);       // 本地事务 1
    enrollmentMapper.insert(studentId, courseId); // 本地事务 2
    // 发 RocketMQ 事务消息（半消息）：通知学生服务加学分
    rocketMQTemplate.sendMessageInTransaction(
        "credit-topic", buildCreditMsg(studentId, courseId), courseId);
}

// 学生服务：监听消息，异步加学分（手动确认 + 幂等 + 死信兜底）
@RocketMQMessageListener(topic = "credit-topic")
public void addCredit(Message msg) {
    // 幂等：按 (studentId + courseId) 去重，防重复加学分
    if (!dedup(msg)) return;
    studentMapper.addCredit(msg.getStudentId(), msg.getCredit());
    // 处理成功才提交 offset
}
```

**保证最终一致的三件套**：
1. **可靠投递**：事务消息（半消息）+ 生产者重试 + 消费者手动确认。
2. **本地消息表兜底**：选课服务在本地事务里同时写「选课记录」和「本地消息表」，定时任务扫描未发送成功的消息重发。
3. **补偿 + 死信队列**：加学分失败重试后进死信队列，定时任务人工介入。

> **权衡**：单体用本地事务（强一致、简单）；微服务用 MQ 最终一致（高性能、牺牲短暂不一致）。面试一定要讲清「为什么最终一致 + 怎么补救」。

## 五、幂等性：防重复选课

### 问题描述

学生选课时出现以下情况都会导致**重复选课**（同一门课占两个名额）：

1. 学生手速快点了两次「选课」按钮。
2. 网络超时，客户端自动重试（第一次其实成功了）。
3. MQ 重复投递（消费失败重试、网络闪断）。

需要保证「同一个学生的同一次选课请求，无论执行多少次，结果和执行一次一样」。

**面试官追问点**：数据库、Redis、Token 三种幂等方案分别怎么实现？各自适用什么场景？

### 完美解决方案

#### 方案一：数据库唯一索引（最可靠，最终兜底）

```sql
-- 复合唯一索引：同一学生同一课程只能一条记录
UNIQUE KEY uk_student_course (student_id, course_id);
```

```java
try {
    enrollmentMapper.insert(studentId, courseId);
} catch (DuplicateKeyException e) {
    // 重复插入说明已选过，直接忽略（天然幂等）
    log.info("重复选课请求，已忽略");
}
```

#### 方案二：Redis 去重（前置拦截，性能高）

```java
// 用 SETNX 做前置去重：返回 false 说明已处理过，直接拒绝/忽略
public String enroll(String studentId, String courseId) {
    String key = "enroll:dedup:" + studentId + ":" + courseId;
    boolean first = redis.setIfAbsent(key, "1", 1, TimeUnit.HOURS);
    if (!first) {
        throw new BizException("请勿重复提交");   // 或直接返回"已选"
    }
    // ... 执行选课逻辑
    return "success";
}
```

#### 方案三：幂等 Token（防重复提交）

```java
// 1. 学生进入选课页时，后端下发唯一 token，存 Redis
String token = UUID.randomUUID().toString();
redis.set("enroll:token:" + studentId, token, 30, TimeUnit.MINUTES);
// 前端提交时带上 token

// 2. 提交时用 Lua 保证「校验 + 删除」原子（防止 token 被并发重复消费）
String script =
    "if redis.call('GET', KEYS[1]) == ARGV[1] then " +
    "  return redis.call('DEL', KEYS[1]) " +
    "else return 0 end";
Long ok = redis.execute(script, List.of("enroll:token:" + studentId), token);
if (ok == 0) throw new BizException("重复提交");
```

#### 方案对比与权衡

| 方案 | 优点 | 缺点 | 适用 |
|------|------|------|------|
| 唯一索引 | 最可靠，DB 层保证 | 有一定写入开销 | 最终兜底，必加 |
| Redis SETNX | 性能高 | Redis 故障需兜底 | 前置拦截 |
| 幂等 Token | 可控制提交粒度 | 需前后端配合 | 表单提交防重 |

> **最佳实践**：**Redis 前置去重（性能）+ 唯一索引兜底（可靠）** 组合，覆盖绝大多数场景。

## 六、课程信息双写一致性（canal + MQ + ES）

### 问题描述

课程信息（课程名、教师、简介、开课时间）需要同时存在于两个数据源：

1. **MySQL**：权威数据源，增删改都在这里。
2. **Elasticsearch**：用于课程搜索（模糊检索、关键词、过滤），承载高并发读。

当教务员**修改课程信息**（如改教师、改上课时间）或**删除课程**时，必须保证 ES 里的数据和 MySQL 一致。如果先写 MySQL 再写 ES，中间失败就会产生**双写不一致**：学生搜到的课程是旧的（已改教师却没更新），或搜到已删除的课程。

**面试官追问点**：为什么不能简单「先写 DB 再写 ES」？canal + MQ 怎么解决？遇到消息丢失/重复怎么办？

### 完美解决方案

#### 方案演进：从「双写」到「binlog 订阅」

**❌ 方案一：应用层双写（有坑）**

```java
@Transactional
public void updateCourse(Course course) {
    courseMapper.update(course);        // 写 MySQL
    esClient.update(course);            // 写 ES —— 若这步失败，两边就不一致了
}
```

> 问题：两步不在同一事务里，ES 写失败导致不一致；且顺序不同（先 ES 后 DB）也可能出问题。

**✅ 方案二：canal 监听 binlog → MQ → ES（推荐）**

```
MySQL 变更 → canal 伪装成从库订阅 binlog → 解析变更事件 → 投递 RabbitMQ
  → ES 同步服务消费 → 更新/删除 ES 索引
```

```java
// canal 监听到的 binlog 变更 → 封装成消息投递到 RabbitMQ
// ES 同步服务消费消息，执行 ES 的增删改
@RabbitListener(queues = "course.sync.queue")
public void syncToEs(CourseChangeEvent event) {
    switch (event.getType()) {
        case INSERT:
        case UPDATE:
            esClient.index("course", event.getId(), event.getData());  // 更新 ES
            break;
        case DELETE:
            esClient.delete("course", event.getId());                   // 删除 ES
            break;
    }
}
```

#### 关键问题与解决

**1. 保证消息不丢（可靠性）**
- canal 本身保证 binlog 不丢（从 MySQL 主从复制机制继承）。
- RabbitMQ 开启**持久化**（消息、队列、交换机都持久化）。
- 消费者**手动确认**（`AcknowledgeMode.MANUAL`），处理成功才 ack。

**2. 保证顺序与幂等（重复消费）**
- 同一课程的变更事件按顺序进同一队列（或用 hash 路由），保证 ES 最终状态正确。
- 消费端按 `(课程ID + binlog 位置/版本号)` 做幂等，重复消息直接忽略。

**3. 兜底对账（最终一致的最后防线）**
- 定时任务扫描 MySQL 与 ES 的数据差异（如按更新时间比对），发现不一致就重新同步。
- 全量重建索引接口，必要时重建整个 ES 索引。

#### 完整链路图

```
教务员修改课程 → MySQL 写入成功(binlog 记录)
  → canal 订阅 binlog → 解析变更 → 投递 RabbitMQ(持久化)
    → ES 同步服务消费(手动确认 + 幂等) → 更新 ES
      → 定时对账任务兜底，修复漏同步/错同步
```

> **权衡**：canal 方案解耦了业务代码（业务只管写 MySQL），异步同步有短暂延迟（通常毫秒~秒级），适合「最终一致」的搜索场景。若要求强一致，才考虑同步双写 + 事务（代价是耦合和高延迟）。

## 附：教务系统面试答题套路

遇到教务场景题，按这个结构答：

1. **先估算**：学生总数、热门课程数、单课并发人数，估算 QPS（如 5000 人抢 50 名额，峰值 QPS 上万），体现工程思维。
2. **定位难点**：明确是「容量超卖」「重复选课」「时间冲突」还是「缓存击穿」，逐一拆解。
3. **分层给方案**：前端防重 → 网关/服务端限流 → Redis 原子扣减 → MQ 异步削峰 → DB 唯一索引 + 条件更新兜底。
4. **讲权衡**：Redis 高性能 vs DB 强一致、最终一致 vs 强一致、锁粒度 vs 并发度。

**高频关键词**：Redis Lua 原子扣减、缓存击穿(逻辑过期)、分布式锁、唯一索引兜底、时间槽唯一索引、MQ 削峰、幂等、最终一致、canal binlog 同步 ES。
