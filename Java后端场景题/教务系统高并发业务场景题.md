## 一、选课抽签制（高并发报名 + 公平抽签）

### 问题描述

很多学校对热门课程不是「先到先得」，而是「**报名 → 抽签 → 中签 → 选课**」的流程。这带来两个高并发/公平性难题：

1. **报名阶段高并发**：上万学生在报名窗口同时提交报名，报名名单不能丢、不能重复报名。
2. **抽签公平性 + 防作弊**：抽签结果必须「随机且可验证」，不能让落选学生怀疑教务员暗箱操作；中签结果要公示且防篡改。
3. **中签后选课**：中签学生需要在规定时间内完成选课，未选则名额释放，同时要防「中签但不选」浪费名额。

**面试官追问点**：
- 报名的高并发写入怎么扛？（Redis 原子写入 + 限流）
- 抽签怎么保证**公平且可验证**？（哈希承诺 / VRF 可验证随机）
- 权重抽签（高年级优先）怎么设计？

### 完美解决方案

#### 第 1 步：报名阶段 —— Redis 原子写入 + 防重 + 限流

```java
// 用 Redis 的 Set 结构保存报名名单，SADD 天然去重 + 原子
// 报名：同一学生同一课程只能报一次
public String signUp(Long studentId, Long courseId) {
    // 1. 限流：防止同一学生狂点（也可以放网关层）
    String limitKey = "signup:limit:" + studentId;
    Long count = redis.incr(limitKey);
    if (count == 1) redis.expire(limitKey, 1, TimeUnit.MINUTES);
    if (count > 10) throw new BizException("操作过于频繁");

    // 2. 报名写入：SADD 原子去重，返回 0 说明已报过名
    Long added = redis.sadd("signup:course:" + courseId, String.valueOf(studentId));
    if (added == 0) throw new BizException("请勿重复报名");

    // 3. 报名成功，异步落库（MQ）做持久化，防止 Redis 丢数据
    mq.send(new SignUpMsg(studentId, courseId));
    return "报名成功，等待抽签";
}
```

> **为什么用 Redis Set**：`SADD` 单命令原子去重，避免「先查后写」的重复报名竞态；Redis 扛住报名瞬间的高并发写，DB 通过 MQ 异步落库。

#### 第 2 步：抽签 —— 哈希承诺（commit-reveal）保证公平可验证

```java
// 核心思想：先公布"随机种子"的哈希承诺，再公布种子本身，任何人都能验证结果
// 步骤 1（抽签前）：教务系统生成随机种子 seed，公开它的哈希 H = SHA256(seed)
// 步骤 2（报名结束后）：公开 seed，任何人都能重算 H 验证 seed 没被中途换过
// 步骤 3（抽签）：用 seed + 学生ID 计算哈希，取模得到是否中签

public boolean isWinner(Long studentId, String seed, int quota, int total) {
    // 用 seed + studentId 做哈希，结果在 [0, total) 内，落在前 quota 即中签
    long hash = Hashing.murmur3_128().hashUnencodedChars(seed + studentId).asLong();
    int bucket = (int) (Math.abs(hash) % total);
    return bucket < quota;
}
```

> **为什么公平可验证**：先公开哈希、再公开种子，教务员无法在「看到报名名单后」再挑一个对自己有利的 seed（因为哈希承诺已公开，换 seed 会对不上）。更高级的做法是用 **VRF（可验证随机函数）** 或未来某个区块的哈希作为公开随机源。

#### 第 3 步：权重抽签（高年级/学分高优先）

```java
// 每个学生分配一个权重区间，随机落在谁的区间谁中签，权重越大区间越大
// 例：大四权重 4、大三权重 3、大二权重 2、大一权重 1
public String weightedDraw(List<Student> signups, String seed) {
    long totalWeight = signups.stream().mapToLong(s -> weight(s.getGrade())).sum();
    long r = Math.abs(hash(seed)) % totalWeight;   // 随机落点
    long cur = 0;
    for (Student s : signups) {
        cur += weight(s.getGrade());
        if (r < cur) return s.getId();              // 落在该学生区间
    }
    return null;
}
```

#### 第 4 步：中签结果公示 + 防篡改 + 超时释放

```java
// 中签结果用 Redis 记录，公示期间任何人都能查
redis.sadd("signup:winner:" + courseId, winnerStudentIds.toArray(new String[0]));

// 中签学生需在截止时间内完成选课，否则名额释放（延迟队列 + 定时任务）
// 选课逻辑复用：Lua 原子扣减 + 判重 + 冲突检测（见《教务系统高难度场景题》）
```

> **权衡**：抽签制牺牲了「先到先得」的即时性，换来了公平性；报名用 Redis 扛高并发，抽签用哈希承诺保证可信，中签结果公示防篡改。

## 二、退课 / 换课（并发回滚容量 + 换课原子性）

### 问题描述

选课不是一锤子买卖，有完整的**退课、换课**流程，这里有两个高并发下的经典难题：

1. **退课并发回滚容量**：学生退课要把课程容量 `capacity + 1`，但退课瞬间可能正有其他学生在抢这个名额。如果并发控制不好，会出现：
   - **超退**：容量回滚后超过总容量上限（原本 50 个名额，退课加多了变成 51）。
   - **回滚与抢课竞争**：退了 1 个名额，同时 2 个人抢，最终超卖。
2. **换课原子性**：换课 = 「退旧课 + 选新课」两步，必须**原子**，否则出现「旧的退了、新的没选上」的中间态。

**面试官追问点**：
- 退课回滚怎么防止超退？（条件更新 + 上限校验）
- 换课怎么保证原子？（Lua 脚本一次完成退+选）
- 选课流程的状态机怎么设计？（待确认 → 已选 → 退课中 → 已退）

### 完美解决方案

#### 第 1 步：选课状态机设计

```
待确认(0) → 已选(1) → 退课中(2) → 已退(3)
                          ↓
                    （取消退课回到 已选）
```

```java
// 状态流转必须校验，非法流转直接拒绝
public void dropCourse(Long studentId, Long courseId) {
    Enrollment e = enrollmentMapper.select(studentId, courseId);
    if (e == null || e.getStatus() != 1) {   // 只有"已选"才能退课
        throw new BizException("当前状态不可退课");
    }
    // 流转到"退课中"，退课成功后再到"已退"
}
```

#### 第 2 步：退课回滚容量 —— 条件更新防超退

```sql
-- ✅ 条件更新：只有 capacity < total_capacity 才回滚，防止超退（容量不能超过总上限）
UPDATE course
SET capacity = capacity + 1
WHERE id = ? AND capacity < total_capacity;
```

```java
// Redis 侧同样用 Lua 保证回滚原子 + 防超退
-- 回滚 Lua 脚本
local capacity = redis.call('GET', KEYS[1])          -- 当前余量
local total = redis.call('GET', KEYS[2])              -- 总容量
if not capacity or tonumber(capacity) >= tonumber(total) then
    return -1   -- 已满，不能回滚（防超退）
end
redis.call('INCRBY', KEYS[1], 1)                      -- 余量 + 1
redis.call('SREM', KEYS[3], ARGV[1])                  -- 从学生已选集合移除
return 1
```

#### 第 3 步：换课原子性 —— Lua 一次完成「退旧 + 选新」

```lua
-- 换课核心 Lua：原子完成「退旧课(余量+1) + 选新课(判重+查冲突+余量-1)」
-- KEYS[1] 旧课余量  KEYS[2] 新课余量  KEYS[3] 学生已选集合  KEYS[4] 学生时间槽集合
-- ARGV[1] 旧课ID  ARGV[2] 新课ID  ARGV[3] 新课时间槽  ARGV[4] 新课总容量
-- ① 退旧课：旧课余量 + 1，学生集合移除旧课
redis.call('INCRBY', KEYS[1], 1)
redis.call('SREM', KEYS[3], ARGV[1])
-- ② 选新课：判重 + 查余量 + 查冲突 + 扣减
if redis.call('SISMEMBER', KEYS[3], ARGV[2]) == 1 then
    return -1   -- 新课已选
end
local newStock = redis.call('GET', KEYS[2])
if not newStock or tonumber(newStock) <= 0 then
    return -2   -- 新课名额已满
end
if redis.call('SISMEMBER', KEYS[4], ARGV[3]) == 1 then
    return -3   -- 新课时间冲突
end
redis.call('DECRBY', KEYS[2], 1)
redis.call('SADD', KEYS[3], ARGV[2])
redis.call('SADD', KEYS[4], ARGV[3])
return 1         -- 换课成功
```

> **为什么换课必须原子**：如果「退旧课」成功但「选新课」失败（名额被抢走），学生就处于「旧课退了、新课没选上」的尴尬状态。Lua 把两步合并成一次 Redis 原子操作，要么全成功要么全失败，天然避免中间态。

#### 第 4 步：时间窗控制 + 幂等

```java
// 只有选课期才能退课/换课，开课后锁定
if (now() > semester.getDropDeadline()) {
    throw new BizException("退课时间已截止");
}

// 退课幂等：同一退课请求不重复回滚容量
boolean first = redis.setIfAbsent("drop:dedup:" + studentId + ":" + courseId, "1", 1, TimeUnit.HOURS);
if (!first) return "已退课，请勿重复操作";
```

> **权衡**：退课回滚用「条件更新 + 上限校验」防超退；换课用「Lua 原子脚本」防中间态；状态机保证流转合法。三者结合才能在高并发下安全。

## 三、消息通知系统（大规模推送 + MQ 削峰）

### 问题描述

教务系统经常要**一次性通知大量学生**，如：成绩发布通知（一门课几百学生）、调停课通知（可能上万学生）、选课结果通知。要求多渠道触达（**站内信 + 短信 + 邮件 + App 推送**），且不能因为推送慢而拖垮主业务流程。

**高并发难点**：
1. **大规模推送**：一次成绩发布要通知几百人，一次调停课要通知上万人，同步发送会阻塞 + 打爆下游。
2. **多渠道适配**：不同通道发送方式不同，失败处理不同。
3. **防重复 + 防打扰**：同一学生不能收到 3 条重复通知，也不能一天被短信轰炸。
4. **可靠性**：短信/邮件发送失败要重试，不能丢。

**面试官追问点**：怎么削峰？多通道怎么设计（策略模式）？怎么保证不丢、不重？

### 完美解决方案

#### 第 1 步：MQ 削峰 —— 主业务只写消息，异步分发

```java
// 成绩发布：主流程只做"发布"这个动作 + 写一条 MQ 消息，通知是异步的
@Transactional
public void publishScore(Long courseId) {
    scoreMapper.updateStatus(courseId, "PUBLISHED");   // 主业务：发布成绩
    // 发 MQ 消息，通知服务异步去给几百个学生发通知
    mq.send(new ScorePublishEvent(courseId));
    // 不在这里同步发短信/邮件，避免阻塞发布接口
}
```

#### 第 2 步：多通道适配 —— 策略模式

```java
// 定义通知通道接口，每个通道一个实现，新增通道不改主流程
public interface NotifyChannel {
    boolean send(NotifyMessage msg);          // 返回是否发送成功
    ChannelType getType();
}

@Component
public class SmsChannel implements NotifyChannel {
    public boolean send(NotifyMessage msg) { /* 调用短信网关 */ }
    public ChannelType getType() { return ChannelType.SMS; }
}
@Component
public class EmailChannel implements NotifyChannel {
    public boolean send(NotifyMessage msg) { /* 调用邮件服务 */ }
    public ChannelType getType() { return ChannelType.EMAIL; }
}
@Component
public class InboxChannel implements NotifyChannel {  // 站内信
    public boolean send(NotifyMessage msg) { /* 写站内信表 */ }
    public ChannelType getType() { return ChannelType.INBOX; }
}

// 通知服务按消息指定的通道，用策略模式分发
@Component
public class NotifyService {
    private final Map<ChannelType, NotifyChannel> channels;

    public NotifyService(List<NotifyChannel> list) {
        this.channels = list.stream().collect(Collectors.toMap(NotifyChannel::getType, c -> c));
    }

    public void dispatch(NotifyMessage msg) {
        for (ChannelType type : msg.getChannels()) {
            boolean ok = channels.get(type).send(msg);
            if (!ok) {
                // 发送失败 → 重试或进死信
                retryQueue.send(msg, type);
            }
        }
    }
}
```

#### 第 3 步：幂等 + 去重 + 频控（防重复、防打扰）

```java
// 1. 幂等：同一事件不重复发送（MQ 重试导致）
public void onNotifyEvent(NotifyEvent event) {
    boolean first = redis.setIfAbsent("notify:dedup:" + event.getEventId(), "1", 24, TimeUnit.HOURS);
    if (!first) return;   // 已处理过
    // ... 分发通知
}

// 2. 频控：一个学生一天最多收 N 条短信，防止轰炸
public boolean canSendSms(Long studentId) {
    String key = "notify:freq:" + studentId;
    Long count = redis.incr(key);
    if (count == 1) redis.expire(key, 1, TimeUnit.DAYS);
    return count <= 10;   // 一天最多 10 条
}
```

#### 第 4 步：可靠性 —— 重试 + 死信 + 批量优化

```java
// 发送失败重试：固定次数后进死信队列，定时任务人工处理
@RabbitListener(queues = "notify.retry.queue")
public void retrySend(NotifyMessage msg) {
    try {
        channels.get(msg.getType()).send(msg);
    } catch (Exception e) {
        if (msg.getRetryCount() >= 3) {
            deadLetterQueue.send(msg);   // 超 3 次进死信，人工介入
        } else {
            msg.setRetryCount(msg.getRetryCount() + 1);
            retryQueue.send(msg);        // 重新投递
        }
    }
}

// 站内信批量插入：几百条站内信一次批量插入，而非逐条 insert
inboxMapper.batchInsert(messageList);
```

#### 完整链路

```
成绩发布 → 写 MQ(通知事件) → 通知服务消费(幂等去重)
  → 策略模式分发到多通道(站内信/短信/邮件/App)
    → 频控检查 → 发送
      → 失败重试(≤3次) → 超限进死信 → 定时任务人工处理
```

> **权衡**：异步推送牺牲了「即时性」（通知可能延迟秒级到达），换来了「主业务不被拖垮 + 能扛住大规模推送」。多通道用策略模式解耦，幂等+频控保证体验，重试+死信保证可靠。

## 四、分库分表 + 冷热分离（支撑高并发读写）

### 问题描述

教务系统的核心表会**逐年累积**，几年后单表上亿行：

- **选课记录**：每学期新增几十万条。
- **成绩记录**：每学期新增。
- **操作日志 / 登录日志**：增长最快，一天几十万条。

单表数据量过大时，即使加了索引，高并发读写也会越来越慢（B+ 树层数变高、缓存命中率下降、写入锁竞争加剧）。需要做**分库分表 + 冷热分离**来支撑高并发。

**面试官追问点**：
- 分表键（sharding key）怎么选？为什么？
- 怎么保证跨分片查询的正确性？
- 冷热数据怎么分离？历史数据怎么归档？

### 完美解决方案

#### 第 1 步：选对分片键（最关键）

| 表 | 分片键 | 理由 |
|----|--------|------|
| 选课记录 | `semester`（学期） | 查询天然按学期过滤，历史学期天然隔离 |
| 成绩记录 | `student_id` 哈希 | 查某个学生成绩时只路由到一个分片 |
| 日志表 | `create_time`（时间） | 按天/月分表，天然冷热分离 |

> **分片键选择原则**：选「查询时一定会带上的字段」，避免跨分片查询。选了 `student_id` 就要让所有查询都带 `student_id`。

#### 第 2 步：ShardingSphere 分片

```yaml
# ShardingSphere 配置：成绩表按 student_id 哈希分 16 个分片
rules:
  - !SHARDING
    tables:
      score:
        actualDataNodes: score_${0..15}      # score_0 ~ score_15
        databaseStrategy:
          standard:
            shardingColumn: student_id
            shardingAlgorithmName: hash_mod
    shardingAlgorithms:
      hash_mod:
        type: HASH_MOD
        props:
          sharding-count: 16
```

```java
// 业务代码无需改动，ShardingSphere 自动按 student_id 路由到对应分片
List<Score> scores = scoreMapper.selectByStudent(studentId);  // 只查一个分片
```

#### 第 3 步：冷热分离 + 归档

```java
// 冷热分离：近期数据（本学期）放"热表"，历史数据归档到"冷表/冷库"
// 热表：只存当前学期 + 上学期，数据量小、读写快
// 冷表：历史学期数据，查询频率低，可放慢存储/归档库

// 归档任务：定时把超过 2 个学期的数据迁到归档表
@Scheduled(cron = "0 0 3 * * ?")   // 每天凌晨 3 点
public void archiveOldData() {
    String archivedSemester = getSemesterBefore(2);   // 2 个学期前的学期
    // 迁移到归档表，然后删除热表数据（或直接物理分表：老数据本来就在老分片）
    archiveMapper.migrate(archivedSemester);
    scoreMapper.deleteBySemester(archivedSemester);
}
```

#### 第 4 步：读写分离（配合分库分表）

```
写请求 → 主库（分片）
读请求 → 从库（分片，分担读压力）
```

```yaml
# 读写分离：主从 + 分片组合
rules:
  - !READWRITE_SPLITTING
    dataSources:
      ds_master: [ds_master_0, ds_master_1]
      ds_slave: [ds_slave_0, ds_slave_1]
    loadBalancers:
      roundRobin:
        type: ROUND_ROBIN
```

#### 分库分表 vs 冷热分离的取舍

| 方案 | 适用 | 优缺点 |
|------|------|--------|
| 分库分表（ShardingSphere） | 单表几千万~上亿，需高并发读写 | 路由复杂、跨分片查询难、运维成本高 |
| 冷热分离 + 归档 | 历史数据查询频率低 | 简单，但热表数据量大时仍需分表 |
| 归档到数仓/冷存储 | 报表分析、历史查询 | 实时性差，适合离线分析 |

> **权衡**：分库分表解决「单表数据量过大导致的性能下降」，但引入「跨分片查询困难、事务变复杂」的成本，**非必要不分表**。一般先「加索引 + 缓存 + 读写分离 + 冷热分离」，实在撑不住才分库分表。面试要体现「先易后难、按需演进」的判断力。

## 附：高并发业务面试答题套路

1. **先判断瓶颈**：是「写并发」（抢课、报名、退课）还是「读并发」（查课表、查成绩），还是「数据量」（分库分表）。
2. **写并发**：Redis 原子操作（Lua/Set/INCRBY）+ 唯一索引兜底 + MQ 削峰。
3. **读并发**：缓存 + 读写分离 + 覆盖索引。
4. **数据量**：冷热分离 → 分库分表 → 归档数仓。
5. **讲权衡**：一致性 vs 性能、原子性 vs 并发度、即时性 vs 异步。

**高频关键词**：Redis 原子操作、哈希承诺/可验证随机、Lua 原子换课、状态机、策略模式多通道、MQ 削峰、幂等、频控、分片键、冷热分离、读写分离。
