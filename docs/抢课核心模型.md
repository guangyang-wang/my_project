# 抢课核心模型 —— 权威扣减源 vs 缓存副本

> 一句话结论：**抢课里的 Redis 不是「数据库的缓存副本」，而是「库存的权威扣减源」。**
> 一致性靠「预扣 + 异步落库 + 回补」保证，而不是「删缓存重建」。
> 本文针对 mock 面试里反复踩坑的概念错位，把模型讲透，和 `抢课功能亮点.md`（讲架构细节）互补。

---

## 一、为什么必须先分清两种模型

大多数缓存知识（Cache Aside、延迟双删、缓存穿透/击穿/雪崩）默认的语境是「Redis 是数据库的只读投影」。但**抢课不是这个语境**。把两个模型混在一起，是所有错误理解的根源。

### 模型 A：缓存副本（Cache Aside 语境）

- **是什么**：Redis 里存的是数据库某行数据的**投影**，数据库是唯一真相。
- **干什么**：读多写少的场景，用 Redis 扛读流量（商品详情、用户信息）。
- **一致性手段**：写库后「删缓存 / 延迟双删」，让下次读回源重建。
- **关键性质**：**缓存删了没关系**，回源重建即可恢复，因为真相在数据库。

### 模型 B：权威扣减源（抢课预扣语境）

- **是什么**：Redis 里的 `stock:{courseId}` 是抢课期间的**权威剩余名额**，Lua 在这里做原子「判断 + 扣减」。
- **干什么**：高并发下，把「判断 + 扣减」下沉到 Redis 单线程，扛住 MySQL 行锁扛不住的吞吐。
- **一致性手段**：Redis 预扣成功 → 发 MQ → 异步落库；落库失败 → **回补 Redis**（不是删）。
- **关键性质**：**stock 不能随便删**，它承载了「已预扣、还没落库」的中间态，删了重建会丢状态。

### 对比表

| 维度 | 模型 A：缓存副本 | 模型 B：权威扣减源 |
|---|---|---|
| Redis 的角色 | 数据库的投影 | 并发扣减的主战场 |
| 真相在哪 | 数据库 | 抢课窗口期在 Redis，最终收敛到 DB |
| 写路径 | 先更库，再删缓存 | 先扣 Redis，再异步更库 |
| 出错了怎么办 | 删缓存，回源重建 | 回补 Redis，等下次重试 |
| 删了 key 会怎样 | 没事，重建即可 | 丢中间态，预扣层失真 |
| 适用场景 | 读多写少（详情页、用户信息） | 高并发扣减（秒杀、抢课、库存） |

> 抢课里的 `stock:{courseId}`、`stu:credit:{studentId}`、`stu:times:{studentId}` 都属于**模型 B**，
> 是预扣状态，不是投影。（`course:times:{courseId}` 是配置快照，另说。）

## 二、抢课完整链路（每层职责 + 为什么放这）

```
学生请求
  │
  ▼
懒加载预热（key 缺失才回源 MySQL，setIfAbsent 防并发重复回源）
  │
  ▼
Lua 脚本：库存 / 时间冲突 / 学分 三项原子「判断 + 扣减」
  │
  ├─ 不通过（-1/-2/-3）──► 抛业务异常，同步返回
  │
  └─ 通过（1）──► 发 RabbitMQ（异步落库，接口同步返回）
                    │
                    ▼
              消费者 persistEnrollment（@Transactional）
                    │
                    ├─ 条件更新 WHERE selected_count < capacity
                    │     ├─ 0 行 ──► 回补 + ack（不重试）
                    │     └─ 1 行 ──► 插入选课记录
                    │           ├─ 撞唯一索引 ──► 回补 + ack
                    │           └─ 成功 ──► ack
                    └─ 其它异常 ──► 回补 + 抛异常重试
```

---

## 三、三层防超卖（每一层防什么）

| 层 | 机制 | 防的是什么 | 为什么需要它 |
|---|---|---|---|
| 第一层 | Redis + Lua 原子预扣 | 并发「都判断通过」 | 主判断，扛高并发；MySQL 行锁把同一行写串行化，扛不住 |
| 第二层 | MySQL 条件更新 `WHERE selected_count < capacity` | 预扣层失真 / 脏数据导致的超卖 | Redis 状态可能被删 / 过期 / 算错，DB 层兜底 |
| 第三层 | 唯一索引 `uk_student_course` | 同一人重复选同一门课 | 幂等 / 防重，重复消费、极端并发最终拦截 |

> 关键区分：**第二层防「超卖」，第三层防「重复」**，是两种不同的失败模式，别混为一谈。

## 四、核心场景推演：stock key 被删 / 过期

假设 `capacity=100`、`selected_count=0`，抢课进行中已有 100 个请求 Lua 预扣成功（stock 100→0），但这 100 条消息还在 MQ 里没落库。

1. **重建值**：下一个请求发现 key 没了，回源 `capacity − selected_count = 100 − 0 = 100`。但真实可抢 = 0。**不准。**
2. **连锁反应**：预扣层失真 → 又多放行 100 个请求 → 全进 MQ → 落库时被第二层（条件更新）拦住。
3. **最终结果**：前 100 个合法消息把 `selected_count` 从 0 写到 100；后 100 个失真消息 `incr` 返回 0 行 → 回补 + ack。**`selected_count` 最终 = 100 = capacity，不超卖。**
4. **代价**：那 100 个失真请求「先显示抢到、最后被回滚」（坏体验）+ MQ 被打无效流量。

> 结论：**stock 是权威扣减源，删了会丢「已预扣未落库」的中间态；但就算丢了，第二层条件更新也能保证最终不超卖。**
> 这正是「预扣层可以错，DB 层兜得住」的设计哲学。

## 五、一致性模型：强一致诉求 vs 最终一致实现

拆成两层看，不能笼统说「强一致」：

1. **不超卖（`selected_count ≤ capacity`）—— 这才是强一致诉求**，靠三层兜底保证（不是靠锁）。
2. **Redis 与 MySQL 数值一致 —— 这是最终一致**。预扣成功 → MQ → 异步写库，中间有几十毫秒到秒级窗口，靠「失败回补 + 幂等 + 对账」收敛。

### 为什么不用这些方案

- **读写锁 / 分布式锁**：写锁排他，高并发吞吐崩；Lua 单线程已原子解决并发；且锁管不到「MQ 异步落库」这个跨系统过程。
- **版本号乐观锁（mock 里提过的那套）**：**类别错误**。乐观锁解决「单行并发写冲突」（CAS：`WHERE version = ?`），管不了「缓存 key 被删了怎么重建」；而且 MySQL 的 `version` 感知不到「已预扣、未落库」的中间态——那 100 个预扣根本没碰 MySQL，`version` 还是旧值。
- **延迟双删（Cache Aside）**：模型 A 的工具，用在模型 B 上不成立。抢课落库失败是「回补」，不是「删缓存」。

## 六、面试易错点清单（本次 mock 踩过的坑）

| 错误说法 | 为什么错 | 正确说法 |
|---|---|---|
| 「Redis 只是缓存，数据库才是真相」 | 抢课窗口期 Redis 是权威扣减源 | Redis 是并发扣减主战场，最终收敛到 DB |
| 「落库用 Cache Aside + 延迟双删」 | 模型 A 工具用在模型 B 上 | 落库失败走回补，不是删缓存 |
| 「加版本号，MySQL 版本最准确」 | MySQL 感知不到预扣中间态；版本号是并发写工具 | 预扣层可错，靠条件更新 + 唯一索引兜底 |
| 「缓存穿透用布隆过滤器」 | 抢课热点 key 的风险是**击穿**，不是穿透 | 先分清穿透 / 击穿 / 雪崩再套用 |

### 附：穿透 / 击穿 / 雪崩（三个别混）

| 现象 | 是什么 | 典型解法 |
|---|---|---|
| 缓存穿透 | 查一个**根本不存在**的数据，每次都打 DB | 空值缓存 / 布隆过滤器 |
| 缓存击穿 | 一个**热点 key 过期**，瞬间大量请求打 DB | 互斥锁 / 逻辑过期 / 不设 TTL |
| 缓存雪崩 | **大量 key 同时过期**，DB 被打垮 | TTL 加随机值 / 多级缓存 |

> 抢课 `stock` 是热点 key，它的风险是**击穿**，所以正确做法是「选课期间不设过期 + 业务主动维护（预扣/回补）」，而不是布隆过滤器。

## 七、一句话记忆

**抢课 = 权威扣减源（不是缓存副本）+ 三层兜底（Lua 预扣 / 条件更新 / 唯一索引）+ 最终一致（回补 + 幂等 + 对账）。**
