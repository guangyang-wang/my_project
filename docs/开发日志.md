### 三、今日知识点

- **登录完整链路**：登录请求（白名单放行）→ Controller → Service 校验/生成 token → 前端存 token → 后续请求带 `Authorization: Bearer xxx` → 拦截器解析 token → 用户信息存 ThreadLocal → Controller 取用。
- **JWT 与拦截器的关系**：JWT（JJWT）**只是个「生成/解析 token 的工具库」，不自带拦截器**；拦截器（`JwtInterceptor`）是自己手写的，负责在请求进来时调 JWT 解析并做放行/拦截判断。
- **JWT 过期机制**：无状态，服务端不存任何状态；过期信息写在 token 的 `exp` 声明里，解析时拿「当前时间」和 `exp` 做本地比对，过期则抛异常。
- **token 有效期**：`jwt.expire: 86400000`（毫秒）= **24 小时**。
- **企业登录与本项目差异**：企业多用 Spring Security / Sa-Token 统一安全框架、双 token（access + refresh）、Redis 主动失效（黑名单/白名单）、登录后查库拿最新用户信息而非全信 token 里的字段，以及登录加固（限流、设备锁、风控）。
- **`user` 是 MySQL 8 保留字**：实体用 `@TableName("`user`")` 加反引号，否则生成的 SQL 语法报错。
- **JWT 密钥长度**：HS256 要求密钥 ≥ 32 字节，所以 `jwt.secret` 配了一长串。

### 三、今日知识点

- **`@RestControllerAdvice`**：全局异常处理的核心注解，配合 `@ExceptionHandler` 在「Controller 之外」统一处理异常，替代每个方法里手写 try-catch。
- **业务异常 vs 系统异常**：业务异常（`BusinessException`）是预期内的分支，message 直接给用户看、不记日志；系统异常（空指针、SQL 异常）是 bug，返回笼统提示 + 记完整堆栈，避免把内部细节（如 NullPointerException 堆栈）暴露给前端。
- **异常处理器匹配优先级**：Spring 会选「最具体」的异常类型匹配对应 handler，所以 `BusinessException` 走业务处理，其余走 `Exception` 兜底，互不冲突。
- **为什么不用 `IllegalArgumentException`**：它和运行时异常区分不开，全局处理器无法精确匹配「业务错误」和「系统错误」，所以自定义 `BusinessException` 精确标记。

### 三、今日知识点

- **时间片维度表设计**：排课时间是「离散且固定」的（每周几第几节），把每个时间片抽象成一条独立记录，课程通过关联表「占用」时间片；时间冲突比对从「区间重叠计算」简化成「查是否有相同时间片」。顺带消灭 `week_type`（单双周）——单周只占奇数周时间片、双周只占偶数周。
- **关系表也需要实体**：`course_time` 这种多对多关系表同样建实体 + Mapper，因为「课程占用哪些时间片（冲突检测）」「某时间片被哪些课占用」都要查它，还能自定义批量插入方法。
- **一人一课 = 幂等/防重，不是分布式锁**：靠 DB 唯一索引 `uk_student_course(student_id, course_id)` 兜底 + Redis `SETNX` 幂等键（key 是 `studentId:courseId`，不是 studentId）。唯一索引是最终保证，无论并发多乱、MQ 重试多少次都不会出现重复选课。
- **教室-时间唯一约束**：同一时间、同一教室只能一节课，用 DB 唯一索引 `uk_time_classroom(time_slot_id, classroom)` + 预校验 + `@Transactional` 解决；**不用 Redis bitmap + Lua**——对低并发 CRUD 是过度设计。
- **`@Transactional` 两个坑**：① `DuplicateKeyException` 必须 catch 后 **rethrow**（不能吞掉），否则异常被吞、事务不感知、不会回滚；② 方法必须 `public`，否则 Spring 代理不生效。
- **批量插入 vs 循环插入**：企业中真正该避免的是 N+1 次 `SELECT`；「拼接多条 `INSERT ... VALUES`」比循环逐条 insert 少数据库往返，且一条 INSERT 天然原子（一行撞唯一索引整条失败），配合事务实现「全成功或全失败」。
- **12306 的库存方案**：区间票（A→C 占 A→B、B→C 两个区间）用「区间库存」模型，内存/Redis 快速扣减 + DB 唯一约束兜底，本质和选课「容量库存 + 唯一索引兜底」同构。

### 四、遇到的问题与解决

1. **`mvn` 命令找不到**：bash 环境里 Maven 不在 PATH 上（用户平时用 IDEA 编译），无法命令行编译验证。解决：手动 review import 和语法，由用户在 IDEA 里编译。

### 三、今日知识点

- **双写不一致的本质**：MySQL 和 ES 是独立存储，没有分布式事务串起来，ES 无版本控制的裸 `save` 是「谁后到谁赢」，MySQL 靠行锁+事务保证的顺序传导不到 ES，导致丢失更新。
- **binlog 方案的本质**：不是「binlog 有序 + MQ 全局有序」，而是 **binlog 有序（权威顺序）+ 按主键分片的局部有序**；分布式 MQ 做不到也没必要全局有序。
- **网络波动 vs 顺序**：顺序靠「单生产者串行发送 + 单分区 FIFO + 单消费者串行」三环保证，网络波动只引入延迟/重试，不引入乱序；乱序只发生在打破串行的时候。
- **一致性三件套**：有序防乱序、幂等防重复、对账防丢失。
- **Canal 部署三坑**：① Canal 1.1.7 依赖 JDK 8（`-XX:PermSize` 在 JDK 11+ 已移除）；② Canal 的 properties **不支持行内注释**（`#` 只在行首算注释，行尾注释会被当成值，导致 `NumberFormatException`）；③ 重复 key 后者覆盖前者（空配置会覆盖有值配置）。

### 四、遇到的问题与解决

1. **找不到 my.ini**：MySQL 是 zip 解压版，默认不带配置文件。解决：在 MySQL 根目录手动创建。
2. **下错 Canal 包**：文件名 `canal-canal-1.1.7.zip` 是 GitHub 源码包（有 `pom.xml`、`deployer/` 等模块），不是部署包。解决：去 releases 下载 `canal.deployer-1.1.7.tar.gz`。
3. **JDK 21 启动失败**：`-XX:PermSize=128m` 在 JDK 11+ 已移除，JVM 起不来（logs 空）。解决：`startup.bat` 加 `set JAVA_HOME=D:\jdk\JDK8` 改用 JDK 8。
4. **重复配置覆盖**：`canal.properties` 里手加的 RabbitMQ 配置被文件末尾原生空配置覆盖。解决：删掉末尾空配置。
5. **行内注释导致 NumberFormatException**：`rabbitmq.host = 192.168.100.128:5672  # 你的 RabbitMQ` 里注释被当成端口号解析。解决：删掉所有行内注释。
6. **sed 误清空 instance.properties**：用 `sed -i 's/[[:space:]]*#.*$//'` 清理中文注释时把整个文件清空。解决：按 Canal 标准模板重建（master.address + filter.regex 已正确写入）。
7. **NPE（待解决）**：`CanalRabbitMQProducer.init` 里 `queueDeclare` 队列名为 null，堆栈在 `ChannelN.validateQueueNameLength`。已定位到 RabbitMQ 连接成功、声明队列时队列名为空，正在查 `queueDeclare` 队列名来源。
