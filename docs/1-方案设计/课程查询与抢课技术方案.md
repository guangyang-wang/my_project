# 课程查询与抢课技术方案

> 本文档是「课程查询 + 抢课」两大核心业务的实现方案，与最终代码一致（面试问答见 `docs/2-面试准备/抢课功能亮点.md` / `docs/2-面试准备/抢课核心模型.md`）。
> 抢课本质是「商城秒杀」的翻版：查询课程（找商品）→ 前置校验（能不能抢）→ Redis Lua 原子判断+扣减 → MQ 异步落库（最终一致）。

---

## 一、需求与整体架构

### 1. 两大核心业务

| 业务 | 对应秒杀概念 | 技术手段 |
|------|-------------|---------|
| 课程查询 | 搜商品 | Elasticsearch（IK 中文分词）+ 回查 MySQL 拼排课 |
| 抢课 | 秒杀下单 | Redis Lua 原子判断+扣减 + RabbitMQ 异步落库 |

### 2. 整体流程图

```
【查询阶段】
GET /course/search?courseNo=xxx&courseName=yyy&pageNum=1&pageSize=10
  → Elasticsearch BoolQuery：courseNo term 精确 + courseName match 分词
  → 回查 MySQL（course_time + time_slot）拼出「周几第几节 + 教室」
  → 返回 CourseSearchVO（课程元数据 + scheduleList）

【抢课阶段】
POST /enroll/{courseId}（学生身份由 JWT 拦截器解析后放 UserContext）
  │
  ▼
① 查课程：selectById + status=1（可选状态校验）
② 懒加载预热 Redis（4 个 key 缺失时回源 MySQL，setIfAbsent 防并发重复回源）
③ Lua 脚本：库存 / 时间冲突 / 学分 三项原子「判断 + 扣减」
   ├─ -1 售罄 / -2 时间冲突 / -3 学分超限 → 抛业务异常，同步返回
   └─ 1 成功 → 发 RabbitMQ（异步落库），接口同步返回
  ▼（MQ 消费端，异步）
④ 条件更新 MySQL 库存（WHERE selected_count < capacity 防超卖）
⑤ 插入选课记录（唯一索引 uk_student_course 兜底）
⑥ 失败回补 Redis（compensate：库存 +1 / 学分减回 / 时间片 srem）
```

### 3. 技术选型

| 技术 | 依赖/组件 | 说明 |
|------|---------|------|
| Elasticsearch | `spring-boot-starter-data-elasticsearch` | Boot 3.5 对应 ES 8.x；需装 IK 分词插件 |
| Canal | 独立部署 | 订阅 MySQL binlog 同步 ES（解决双写不一致） |
| 其余 | 已有 | Redis / RabbitMQ / MyBatis-Plus 无需新增 |

> 备注：ES 是「搜索」用的，与抢课逻辑解耦。ES 与 MySQL 的一致性用 Canal 订阅 binlog 解决（见 `docs/2-面试准备/面试亮点-ES双写一致性.md`）。

## 二、数据库设计

### 1. 课程信息表 `course`

```sql
CREATE TABLE `course` (
    `id`                BIGINT       NOT NULL AUTO_INCREMENT COMMENT '主键，自增',
    `course_no`         VARCHAR(32)  NOT NULL COMMENT '课程编号（业务唯一，如 CS101），选课/展示用',
    `course_name`       VARCHAR(128) NOT NULL COMMENT '课程名称',
    `category`          TINYINT      NOT NULL DEFAULT 1 COMMENT '课程类别：1=必修 2=选修 3=公选 4=实践',
    `credit`            DECIMAL(3,1) NOT NULL COMMENT '学分（如 3.0、2.5，支持半学分）',
    `hours`             INT          NOT NULL COMMENT '总学时',
    `teacher_name`      VARCHAR(64)  NOT NULL COMMENT '任课教师姓名（冗余展示；正规做法是 teacher_id 关联教师表）',
    `college`           VARCHAR(64)  NOT NULL COMMENT '开课院系/学院',
    `major`             VARCHAR(64)  DEFAULT NULL COMMENT '开课专业（NULL=不限专业）',
    `campus`            VARCHAR(64)  DEFAULT NULL COMMENT '校区（可空）',
    `exam_type`         VARCHAR(32)  DEFAULT NULL COMMENT '考试形式：考试/考查/论文/机考',
    `language`          VARCHAR(32)  DEFAULT NULL COMMENT '授课语言：中文/英文/双语',
    `term`              VARCHAR(32)  NOT NULL COMMENT '开课学期，如 2026-2027-1',
    `capacity`          INT          NOT NULL COMMENT '选课人数上限（= 总库存，核心！）',
    `selected_count`    INT          NOT NULL DEFAULT 0 COMMENT '已选人数（当前库存，异步落库时 +1）',
    `select_start_time` DATETIME     DEFAULT NULL COMMENT '选课开始时间（时间窗）',
    `select_end_time`   DATETIME     DEFAULT NULL COMMENT '选课结束时间（时间窗）',
    `restrict_grade`    VARCHAR(255) DEFAULT NULL COMMENT '限选年级（逗号分隔，如 2024,2025；NULL=不限）',
    `restrict_major`    VARCHAR(255) DEFAULT NULL COMMENT '限选专业（逗号分隔；NULL=不限）',
    `status`            TINYINT      NOT NULL DEFAULT 0 COMMENT '状态：0=未开放 1=可选 2=已满 3=已结束 4=下架',
    `create_time`       DATETIME     DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    `update_time`       DATETIME     DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    `deleted`           TINYINT      NOT NULL DEFAULT 0 COMMENT '逻辑删除：0=未删 1=已删',
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_course_no` (`course_no`),
    KEY `idx_term_status` (`term`, `status`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='课程信息表';
```

### 2. 时间片维度表 `time_slot`（预置 756 条）

```sql
CREATE TABLE `time_slot` (
    `id`      BIGINT  NOT NULL AUTO_INCREMENT COMMENT '时间片ID（全局唯一，多门课复用）',
    `week`    TINYINT NOT NULL COMMENT '第几周：1~18',
    `weekday` TINYINT NOT NULL COMMENT '星期几：1=周一 … 7=周日',
    `section` TINYINT NOT NULL COMMENT '第几节：1~6',
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_week_weekday_section` (`week`, `weekday`, `section`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='时间片维度表（18周×7天×6节=756条）';
```

**为什么用「时间片维度表」而不是「区间」**：
- 大学排课时间是「离散且固定」的（第几周、星期几、第几节），把每个时间片抽象成独立记录，课程通过关联表「占用」某些时间片；
- 时间冲突比对从「区间重叠计算」简化成「查是否有相同时间片 id」；
- 顺带消灭 week_type（单双周）：单周只占奇数周时间片，双周只占偶数周。

### 3. 课程-时间片关联表 `course_time`（多对多）

```sql
CREATE TABLE `course_time` (
    `id`           BIGINT      NOT NULL AUTO_INCREMENT COMMENT '主键',
    `course_id`    BIGINT      NOT NULL COMMENT '课程ID（关联 course.id）',
    `time_slot_id` BIGINT      NOT NULL COMMENT '时间片ID（关联 time_slot.id）',
    `classroom`    VARCHAR(64) DEFAULT NULL COMMENT '上课教室（属于"课程+时间片"组合）',
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_course_slot` (`course_id`, `time_slot_id`),
    UNIQUE KEY `uk_time_classroom` (`time_slot_id`, `classroom`),
    KEY `idx_time_slot_id` (`time_slot_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='课程-时间片关联表（多对多）';
```

- `uk_time_classroom(time_slot_id, classroom)`：同一时间、同一教室只能排一门课，是排课冲突的最终兜底；
- `classroom` 放这里（而非 time_slot）：同一个时间片可能被多门课占用，教室是「某门课 + 某个时间片」组合的属性。

### 4. 选课记录表 `enrollment`

```sql
CREATE TABLE `enrollment` (
    `id`          BIGINT       NOT NULL AUTO_INCREMENT COMMENT '主键',
    `student_id`  BIGINT       NOT NULL COMMENT '学生ID（关联 user.id）',
    `student_no`  VARCHAR(32)  NOT NULL COMMENT '学号（冗余，便于查询）',
    `course_id`   BIGINT       NOT NULL COMMENT '课程ID',
    `course_no`   VARCHAR(32)  NOT NULL COMMENT '课程编号（冗余）',
    `course_name` VARCHAR(128) NOT NULL COMMENT '课程名称（快照，选课时固化）',
    `credit`      DECIMAL(3,1) NOT NULL COMMENT '学分（快照，选课时的学分）',
    `term`        VARCHAR(32)  NOT NULL COMMENT '学期',
    `status`      TINYINT      NOT NULL DEFAULT 0 COMMENT '状态：0=已选 1=已退课 2=已完成 3=已取消(抢课失败回滚)',
    `select_time` DATETIME     DEFAULT CURRENT_TIMESTAMP COMMENT '选课时间',
    `create_time` DATETIME     DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    `update_time` DATETIME     DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    `deleted`     TINYINT      NOT NULL DEFAULT 0 COMMENT '逻辑删除',
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_student_course` (`student_id`, `course_id`),  -- ★ 一人一课的最终兜底
    KEY `idx_student_term` (`student_id`, `term`),
    KEY `idx_course_id` (`course_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='选课记录表';
```

> **`uk_student_course(student_id, course_id)` 是整个抢课防重的根基**，必须先建。后面 MQ 重复投递、并发重复请求，最终都由它挡下。

### 5. Redis key 设计

| key | 类型 | 值 | 用途 |
|-----|------|-----|------|
| `stock:{courseId}` | String | 剩余名额（capacity - selected_count） | Lua 库存判断 + 扣减 |
| `course:times:{courseId}` | Set | 该课占用的时间片 id | Lua 时间冲突判断 |
| `stu:credit:{studentId}` | String | 学生已选学分 ×10（整数） | Lua 学分上限判断 |
| `stu:times:{studentId}` | Set | 学生已占用的时间片 id | Lua 时间冲突判断 |

> 四个 key 都是「懒加载预热」：抢课时发现缺失才回源 MySQL 加载一次（`setIfAbsent` 防并发重复回源），之后由 Lua 实时维护。

## 三、抢课前置校验（能不能抢）

实际实现把「库存 / 时间冲突 / 学分」三项判断全部下沉到 Lua 原子执行；进入 Lua 前只做「课程存在 + status=1」的粗校验。

| 校验项 | 判断位置 | 说明 |
|--------|---------|------|
| 课程存在 + status=1 | `enroll()` 查 MySQL | `selectById` + `status != 1` 拒绝 |
| 库存充足 | Lua | `stock < 1` 返回 -1（售罄） |
| 时间冲突 | Lua | 课程时间片集合 ∩ 学生已占时间片集合 ≠ ∅ 返回 -2 |
| 学分上限 | Lua | 已选学分 + 本课学分 > 30 返回 -3 |

> 未实现（可作扩展）：选课时间窗（select_start_time ~ select_end_time）、限选年级/专业。

### 时间冲突检测

用「时间片 id 集合交集」：课程占用时间片集合 `course:times:{courseId}`，学生已占时间片集合 `stu:times:{studentId}`，两者有交集即冲突。

### 学分上限

学分统一 ×10 存整数（30 学分 = 300），Lua 里做整数比较，避免浮点精度问题。

## 四、抢课主流程（Redis Lua + RabbitMQ）

### 1. Lua 脚本（三条件原子判断 + 扣减）

```lua
-- KEYS[1] = stock:{courseId}
-- KEYS[2] = stu:credit:{studentId}
-- KEYS[3] = stu:times:{studentId}
-- KEYS[4] = course:times:{courseId}
-- ARGV[1] = 本课学分 ×10
-- ARGV[2] = 学分上限 ×10（= 300）
-- 返回：1=成功  -1=售罄  -2=时间冲突  -3=学分超限

local stock = tonumber(redis.call('get', KEYS[1]))
if not stock or stock < 1 then return -1 end

local courseTimes = redis.call('smembers', KEYS[4])
for _, t in ipairs(courseTimes) do
    if redis.call('sismember', KEYS[3], t) == 1 then return -2 end
end

local credit = tonumber(redis.call('get', KEYS[2]) or '0')
if credit + tonumber(ARGV[1]) > tonumber(ARGV[2]) then return -3 end

redis.call('decr', KEYS[1])
redis.call('incrby', KEYS[2], ARGV[1])
for _, t in ipairs(courseTimes) do
    redis.call('sadd', KEYS[3], t)
end
return 1
```

> 为什么用 Lua：`判断` + `扣减` 是多个 Redis 命令，拆开发会有并发窗口（同时读到「够」然后都扣 → 超卖）。Redis 单线程串行执行 Lua，脚本内命令一次性执行完，天然原子，不需要额外加锁。

### 2. Service 主流程（enroll）

1. `UserContext.get()` 拿当前学生（拦截器解析 JWT 后放 ThreadLocal）；
2. `selectById` 查课程，校验存在 + `status=1`；
3. 懒加载预热 `ensurePreheated`：4 个 key 缺失才回源 MySQL，`setIfAbsent` 保证只有第一个写进去生效；
4. 执行 Lua（4 KEYS + 2 ARGV），返回值 -1/-2/-3 抛不同业务异常；
5. 通过后发 MQ（`EnrollMessage`：学生 + 课程快照），接口同步返回。

### 3. MQ 消费端（异步落库 + 补偿）

- `persistEnrollment`（`@Transactional`）：`incrSelectedCount`（条件更新 `WHERE selected_count < capacity`）扣库存 + `insert` enrollment；
- 0 行（已满）→ `compensate` 回补 + ack 丢弃；
- `DuplicateKeyException`（撞唯一索引）→ `compensate` + ack 丢弃；
- 其它异常（DB 挂等）→ `compensate` + 抛异常交给 MQ 重试。

**三个关键点**：
1. **防超卖三层**：Redis Lua 拒 + MySQL 条件更新 `WHERE selected_count < capacity` 拒 + 唯一索引 `uk_student_course` 拒。
2. **最终一致**：Redis 先扣（快）、MySQL 后扣（慢），失败靠「回补 Redis」补偿。
3. **消费端幂等**：先查是否已存在 + 唯一索引捕获 DuplicateKey，保证不重复落库。

## 五、一人一课：并发与防重（捋清「分布式锁」）

### 三个概念别混

| 概念 | 解决的问题 | 本项目对应 | 解法 |
|------|-----------|-----------|------|
| 库存并发扣减 | 多人抢同一份资源互斥 | 多学生抢同一门课 | Lua 原子（不需要锁） |
| 幂等/防重 | 同一请求别执行两次 | 同一学生重复抢同一课 | 唯一索引 + 时间冲突拦截 |
| 分布式锁 | 跨多步操作的互斥 | （本项目没有） | Redisson 等，用不到 |

### 本项目防重的两层

1. **数据库唯一索引 `uk_student_course(student_id, course_id)`（必须）**：无论并发多乱、MQ 重试多少次，DB 里绝无重复记录。
2. **时间冲突自然拦截**：同一学生第一次抢成功后，该课时间片已进入 `stu:times`，第二次再抢必命中「时间冲突 -2」。

> 不单独加 setnx 幂等键：第一次成功后时间片已占用，重复抢天然被「时间冲突」拦截，无需额外去重标记。

### 为什么不用「学生 id 做分布式锁」

1. **粒度太粗**：key 只有 studentId，会把这个学生「选 A 课」「选 B 课」全部串行化，白白降低吞吐。
2. **方向反了**：你要防的是「同一学生重复抢同一课」，锁的资源应是 `studentId + courseId`，而不是学生的所有操作。
3. **有更简单的**：防重本质是幂等，唯一索引 + 时间冲突拦截就够了，真上分布式锁（带续期/释放）反而复杂。

> 结论：**别用「学生 id 分布式锁」，用「唯一索引 + 时间冲突拦截」**。这才是企业做法，也更好写。

## 六、Elasticsearch 课程搜索

### 1. 索引设计（CourseDoc，只存搜索/展示字段）

| 字段 | 类型 | 说明 |
|------|------|------|
| `courseNo` / `term` | keyword | 精确匹配（编号、学期） |
| `courseName` / `teacherName` / `college` / `major` | text（ik_max_word 索引 / ik_smart 搜索） | 中文分词 |
| `category` / `credit` / `capacity` / `selectedCount` / `status` | 数值 | 过滤 / 展示 |

> 排课时间、教室不存 ES，点详情回查 MySQL（course_time + time_slot）。实时库存以 Redis 为准，ES 不存库存。

### 2. 数据同步：Canal 订阅 binlog + RabbitMQ

- 放弃业务代码双写，改由 Canal 订阅 MySQL binlog → RabbitMQ → `CourseSyncListener` → ES；
- 顺序：binlog 有序 + 单消费者串行消费；
- 幂等：`save` 按 id upsert；
- 逻辑删除：`@TableLogic` 的删除在 binlog 里是 `UPDATE deleted=1`，消费端判断后删 ES 文档。

> 详见 `docs/2-面试准备/面试亮点-ES双写一致性.md`。

## 七、注意事项（坑）

1. **Redis 和 MySQL 库存最终一致，不是强一致**：Redis 先扣、MySQL 后扣，中间有短暂窗口，靠「回补 + 幂等」收敛。
2. **消费端必须幂等**：MQ 会重复投递，靠「先查 + 唯一索引捕获 DuplicateKey」。
3. **库存字段别放 ES**：ES 近实时延迟会让库存显示不准，实时库存以 Redis 为准。
4. **学分为小数**：用 `DECIMAL(3,1)` + `BigDecimal`，Lua 里 ×10 存整数比较，别用 float/double。
5. **`user` 是保留字要加反引号**：实体 `@TableName("`user`")` 已处理。
6. **批量插入排序防死锁**：`course_time` 多值 INSERT 逐行加锁，插入前对 timeSlotIds 排序，统一加锁顺序。
7. **`@Transactional` 两个坑**：① `DuplicateKeyException` 必须 catch 后 rethrow（不能吞），否则异常被吞、事务不感知、不会回滚；② 方法必须 public，否则 Spring 代理不生效。
