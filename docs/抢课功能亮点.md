# 抢课功能 —— 项目亮点整理

> 一句话概括：**用「Redis + Lua 原子预扣 + MQ 异步落库 + MySQL 条件更新 / 唯一索引兜底」实现了秒杀式抢课，解决了高并发下的超卖与三类业务约束校验问题。**

---

## 一、业务背景与难点

抢课和传统秒杀最大的不同，是**多了一道业务约束**——不只是减库存，还要同时满足三个条件：

1. **库存**：课程还有剩余名额；
2. **时间冲突**：同一时间片只能上一门课；
3. **学分上限**：学生已选总学分不超过 30。

三个条件都是高频读、要实时判断，如果直接打 MySQL，并发一高就扛不住；如果拆成多条 Redis 命令，两个请求会同时读到「够」然后都扣，导致超卖。

---

## 二、架构设计

> 核心思想：**判断与扣减全部下沉 Redis，用 Lua 保证原子性；MySQL 只做异步落库和最终兜底。**

```
学生请求
   │
   ▼
懒加载预热 Redis（4 个 key 缺失时回源 MySQL）
   │
   ▼
Lua 脚本：库存 / 时间冲突 / 学分 → 原子判断 + 扣减
   │
   ├── 不通过（-1/-2/-3）──► 抛业务异常，同步返回
   │
   └── 通过（1）──► 发 RabbitMQ ──► 消费者 @Transactional 落库
                                          │
                                          ├── 成功 ──► ack
                                          ├── 超卖/重复 ──► 回补 Redis + ack
                                          └── 系统异常 ──► 回补 Redis + 抛异常重试
```

### Redis Key 设计

| Key | 类型 | 含义 | 预热值 |
|---|---|---|---|
| `stock:{courseId}` | String | 剩余名额 | `capacity - selected_count` |
| `course:times:{courseId}` | Set | 该课占用的时间片 id | `course_time.time_slot_id` |
| `stu:credit:{studentId}` | String | 已选学分 ×10（整数） | `SUM(credit)×10` |
| `stu:times:{studentId}` | Set | 学生已占用的时间片 id | 已选课程 join course_time |

---

## 三、三个核心设计点

### 1. Lua 原子化「判断 + 扣减」

- Redis 单线程执行 Lua，脚本内 `GET / SMEMBERS / SISMEMBER / DECR / INCRBY / SADD` 顺序一次性执行完，中间不会被别的请求插入，天然原子。
- 返回值约定：`1` 成功 / `-1` 售罄 / `-2` 时间冲突 / `-3` 学分超限，Java 侧据此抛不同业务异常。

### 2. 三层防超卖兜底（层层收口）

| 层 | 机制 | 作用 |
|---|---|---|
| 第一层 | Redis + Lua 预扣 | 高性能扛并发，主判断 |
| 第二层 | MySQL 条件更新 `WHERE selected_count < capacity` | 消息重复 / 缓存脏时兜底 |
| 第三层 | 唯一索引 `uk_student_course(student_id, course_id)` | 极端并发重复选课最终拦截 |

### 3. 最终一致性：回补 + 幂等

- 发 MQ 失败、落库超卖、撞唯一索引 → 都走 `compensate` 回补（库存 `incr`、学分 `decrement`、时间片 `srem`）。
- 消费者先查重做幂等，避免重复消费重复扣。

---

## 四、一致性模型：强一致诉求 vs 最终一致实现

抢课的一致性要拆成两层看，**不能笼统说「强一致」**：

**第一层：库存准确性（不超卖 / 不少卖）—— 这才是「强一致」的真正诉求**
靠三层兜底保证，而不是靠锁：

- Lua 原子预扣（并发安全）；
- MySQL 条件更新 `WHERE selected_count < capacity`（兜底）；
- 唯一索引 `uk_student_course`（最终拦截）。

**第二层：缓存与数据库的数据一致 —— 这是「最终一致」**
Redis 预扣成功 → 发 MQ → 消费者异步写 MySQL，中间有几十毫秒到秒级的窗口，Redis 扣了但 MySQL 还没写。这是异步落库的固有特性，靠「失败回补 + 幂等 +（可选）对账」保证最终一致。

### 为什么不用读写锁 / 分布式锁保证「强一致」？

1. **场景是读多写少**：读写锁的写锁是排他的，会阻塞所有读，高并发下吞吐直接崩，和秒杀目标背道而驰。
2. **Lua 已经解决了并发问题**：Redis 单线程串行执行 Lua，脚本内「判断 + 扣减」天然原子，再加读写锁是重复的、纯损耗。
3. **读写锁锁不住异步落库的延迟**：锁加在 Redis 上，只能管 Redis 内部读写，管不到「MQ 消费者异步写 MySQL」这个跨系统过程——想锁的「缓存和 DB 一致」，锁根本够不着。

> 结论：「不超卖」用 Lua + 条件更新 + 唯一索引保证；「缓存和 DB 一致」用最终一致（回补 + 幂等）保证。两者都不需要也不应该用读写锁。

### 边界：管理员直接改课表怎么办？

抢课依赖的 Redis key 里，有两个是「配置快照」，管理员改课表会让它们过期：

| key | 受哪次改动影响 |
|---|---|
| `stock:{courseId}`（容量部分） | 改 `course.capacity` |
| `course:times:{courseId}` | 改 `course_time`（时间片） |

（`stu:credit` / `stu:times` 是学生状态，由抢课 / 退课维护，不归管理员改课表管。）

两类解法：

1. **业务冻结（推荐，最干净）**：选课开放后（`status=1`）禁止改容量 / 学分 / 时间片。排课、课程管理是选课前 / 后的独立业务——这正是「管理员改课表」和「抢课」应该解耦的原因。抢课周期内快照永远有效，不存在过期问题。
2. **技术失效（若要支持抢课中改课表）**：
   - 管理端写路径主动删对应 key（Cache Aside），下次抢课懒加载重建；
   - 或复用项目已有的 Canal + RabbitMQ 链路，监听 `course` / `course_time` 的 binlog，消费端失效 Redis key，管理端无需感知缓存。

> 取舍：第一版用「业务冻结」，把「管理员改课表」明确划成选课之外的业务；需要抢课中动态调容量时，再上 Canal 失效。

## 五、简历版（可直接放项目经历 bullet）

**项目：选课系统 —— 高并发抢课模块**

- 针对选课高峰高并发场景，采用**秒杀架构**：抢课判断全部下沉 Redis，用 **Lua 脚本把「库存 / 时间冲突 / 学分上限」三项校验 + 扣减合并为一个原子操作**，从根上消除并发下「都判断通过」导致的超卖。
- 同步预扣成功后发 **RabbitMQ 异步落库**，削峰解耦；MySQL 层用**条件更新 `WHERE selected_count < capacity` + 唯一索引 `uk_student_course`** 做双重最终兜底，保证缓存与数据库最终一致。
- 设计**懒加载预热 + 失败回补**机制：Redis key 缺失时回源 MySQL 一次性加载，落库 / 发消息失败时回补库存、学分、时间片，用户可重试。
- 关键技术点：`StringRedisTemplate + DefaultRedisScript`、学分 ×10 存整数规避浮点精度、时间冲突用 Set 交集判断、消息幂等消费、`@Transactional` 接口代理调用。

## 六、面试版问答（可深挖的点）

### 1. 为什么学分要 ×10 存整数？

`credit` 是 `DECIMAL(3,1)`（3.0、2.5），Lua 里浮点比较有精度坑，统一 ×10 存整数（30 学分 = 300），用 `tonumber` 做整数比较。

### 2. 重复抢同一门课怎么拦？

不用单独去重标记。第一次成功后该课时间片已进 `stu:times` 集合，第二次再抢必命中「时间冲突 -2」。

### 3. `@Transactional` 为什么生效？

`persistEnrollment` 是事务方法，消费者注入的是 `EnrollService` 接口而非实现类，通过代理调用事务才生效，规避了 self-invocation 失效问题。

### 4. 懒加载预热怎么防并发重复回源？

用 `setIfAbsent` 保证只有第一个写进去的生效，回源结果幂等。

### 5. Redis 和 MySQL 长期不一致怎么办？

第一版靠回补兜底，后续可用「对账定时任务」定期比对修复（可作为扩展方向）。

### 6. 为什么不用分布式锁 / 读写锁保证一致性？

场景读多写少，写锁排他会拖垮吞吐；Lua 已原子解决并发问题；且锁管不到 MQ 异步落库的跨系统延迟。所以「不超卖」用三层兜底、「缓存和 DB 一致」用最终一致方案，不用锁。

### 7. 消息积压 / 顺序性？

每人每课一条消息，靠唯一索引幂等，顺序不影响最终结果。

### 8. 抢课过程中管理员改了课程容量 / 时间片怎么办？

这是「缓存失效」边界。最简单是业务冻结：选课开放后禁止改容量 / 学分 / 时间片，把管理员改课表划成选课之外的业务。若要支持抢课中动态调容量，用 Cache Aside 主动删 key 或复用 Canal 监听 binlog 失效 Redis。

## 七、扩展方向（可选）

- **对账定时任务**：定期比对 Redis 与 MySQL，修复长期不一致。
- **死信队列**：系统级异常消息进入死信队列，人工介入而非无限重试。
- **预热优化**：热门课程提前批量预热，避免第一次请求回源 MySQL 的冷启动。
- **Canal 失效 Redis 缓存**：复用已有 Canal + RabbitMQ 链路，监听 `course` / `course_time` 变更，消费端删除对应 Redis key，支持抢课中动态调整课程配置。
