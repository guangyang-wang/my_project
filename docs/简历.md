## 项目简介

**高校教务选课系统**（个人项目 · 独立开发 · Spring Boot 3.5 / Java 21）

一个高并发的选课教务系统，覆盖**用户认证、课程管理、排课、选课（抢课）、课程搜索**五大模块。核心解决三个工程难题：选课高峰高并发下的**库存超卖**、课程数据在 MySQL 与 ES 之间的**双写不一致**、以及排课**同教室同时间冲突**与并发**死锁**。

**技术栈**：Spring Boot 3.5、Java 21、MyBatis-Plus、MySQL 8、Redis（Lua 脚本）、RabbitMQ、Elasticsearch 8、Canal、JWT（JJWT）、BCrypt、knife4j

## 核心亮点（问题 → 方案）

### 一、高并发抢课（秒杀式架构）

- 为解决选课高峰高并发下 **MySQL 扛不住压力**的问题，采用 **Redis 做库存扣减逻辑**，把「库存 / 时间冲突 / 学分上限」三项判断与扣减全部下沉到 Redis。
- 为解决拆成多条 Redis 命令导致「**并发都判断通过、超卖**」的问题，采用 **Lua 脚本把判断与扣减合并为单个原子操作**（Redis 单线程串行执行）。
- 为解决同步落库阻塞、**数据库写压力过大**的问题，采用 **RabbitMQ 异步落库削峰**，预扣成功后接口立即返回。
- 为解决**缓存与数据库最终一致**的问题，采用「**条件更新 `WHERE selected_count < capacity` + 唯一索引 `uk_student_course`**」双重兜底，落库失败回补 Redis + 幂等消费。
- 为解决**学分浮点比较精度丢失**的问题，采用**学分 ×10 存整数**、在 Lua 里做整数比较。

### 二、课程搜索与 ES 双写一致

- 为解决课程名 / 教师需**中文分词搜索**的问题，采用 **Elasticsearch 8 + ik_smart 分词**，编号 `term` 精确匹配、名称 `match` 模糊匹配。
- 为解决 MySQL 与 ES 业务双写「**旧数据覆盖新数据**」的丢失更新问题，采用 **Canal 订阅 binlog + RabbitMQ 异步同步**，以 binlog 权威顺序保证同一门课程的变更按提交顺序落到 ES。
- 为解决**消息重复 / 丢失**导致的不一致问题，采用**幂等 upsert + 定时对账兜底**。

### 三、排课冲突控制

- 为解决**同教室同时间冲突**（区间重叠计算复杂易错）的问题，采用**时间片维度表建模**，把冲突检测简化为时间片 id 集合比对。
- 为解决**并发批量插入产生死锁**的问题，采用**批量插入前锁排序**统一加锁顺序。
- 为解决**并发冲突最终兜底**的问题，采用**前置校验 + 联合唯一索引 `uk_time_classroom`** 双层方案。

### 四、用户认证与工程基建

- 为解决**认证无状态、可扩展**的问题，采用 **JWT + 拦截器 + ThreadLocal** 传递登录态。
- 为解决**密码明文存储**的安全问题，采用 **BCrypt 加密**。
- 为解决**接口返回结构不统一、异常堆栈泄露**的问题，采用**统一返回 Result + 全局异常处理**（业务 / 系统异常分流）。

- **已实现（可放心写进简历）**：登录认证、课程管理（增删改查）、排课、ES 搜索 + 双写一致、抢课选课。
- **规划中（暂未实现，简历里不要写成「已完成」）**：成绩管理、培养方案管理、学籍与毕业审核。若面试官问「还有哪些模块」，可主动说明这是下一步规划，体现对教务业务全景的理解，而非已完成。

### 面试官可能追问的「软肋」与应对

1. **「抢课最终一致，窗口期用户看到什么？」** —— 承认异步落库有几十毫秒到秒级窗口，Redis 已扣但 MySQL 未写；靠幂等 + 回补 + 对账收敛，这是「缓存/搜索副本的正确姿势」（最终一致），强一致要上分布式事务、代价过高。
2. **「并发量到底多少？压测了吗？」** —— 诚实说明：功能已实现，压测（JMeter）在后续计划里，但架构按秒杀标准设计（Redis 扛读 + MQ 削峰 + 唯一索引兜底），可现场讲清每层怎么扛并发。
3. **「为什么选 RabbitMQ 不选 Kafka？」** —— 课程变更量极小、技术栈已有 RabbitMQ，单机即跑运维最省；顺序性靠「按主键分片 + 单消费者串行」保证，无需 Kafka 分区顺序。（详见 `面试亮点-ES双写一致性.md` Q6）
