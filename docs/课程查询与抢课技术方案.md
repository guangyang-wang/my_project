
# 课程查询与抢课技术方案

> 本文档是「课程查询 + 抢课」两大核心业务的实现计划书，按部就班照做即可。
> 抢课本质是「商城秒杀」的翻版：查询课程（找商品）→ 前置校验（能不能买）→ Redis 扣库存（Lua 原子）→ MQ 异步落库（最终一致）。

---

## 一、需求与整体架构

### 1. 两大核心业务

| 业务 | 对应秒杀概念 | 技术手段 |
|------|-------------|---------|
| 课程查询 | 搜商品 | Elasticsearch（IK 中文分词） |
| 抢课 | 秒杀下单 | Redis Lua 扣库存 + RabbitMQ 异步落库 |

### 2. 整体流程图

```
【查询阶段】
GET /course/search?keyword=数学
  → Elasticsearch 按 课程名/教师/专业/教室 分词搜索
  → 拿到课程 id 列表
  → 批量查 Redis 补上「实时剩余名额」
  → 返回课程列表（元数据 + 剩余名额）

【抢课阶段】
POST /course/enroll  { courseId }
  │
  ▼
① 前置校验（全在本机/Redis 判断，快速失败）
② Lua 原子扣 Redis 库存
③ 发 MQ 消息（异步落库）
④ 立即返回「抢课成功（处理中）」
  │
  ▼（MQ 消费端，异步）
⑤ 条件更新 MySQL 库存（防超卖）
⑥ 插入选课记录（唯一索引兜底）
⑦ 失败则回补 Redis 库存
```

### 3. 技术选型（新增依赖）

| 技术 | 依赖坐标 | 说明 |
|------|---------|------|
| Elasticsearch | `spring-boot-starter-data-elasticsearch` | Boot 3.5 对应 ES 8.x；需装 IK 分词插件 |
| 其余 | 已有 | Redis / RabbitMQ / MyBatis-Plus 都不用新增 |

> 备注：ES 是「搜索」用的，**和抢课逻辑完全解耦**。如果 ES 环境一时搭不起来，可以先用 MySQL `LIKE` 把查询跑通，搜索部分留到最后再接 ES（见第七节 Step 6）。

## 二、数据库设计

### 1. 课程信息表 `course`

> 你原来列的字段（课程名/学分/教师/专业/排课时间/教室/学时/考试形式/语言）都保留，但补上「选课核心字段」并把「排课时间」拆出去。

```sql
CREATE TABLE `course` (
    `id`                BIGINT       NOT NULL AUTO_INCREMENT COMMENT '主键，自增',
    `course_no`         VARCHAR(32)  NOT NULL COMMENT '课程编号（业务唯一，如 CS101），选课/展示用',
    `course_name`       VARCHAR(128) NOT NULL COMMENT '课程名称',
    `category`          TINYINT      NOT NULL DEFAULT 1 COMMENT '课程类别：1=必修 2=选修 3=公选 4=实践',
    `credit`            DECIMAL(3,1) NOT NULL COMMENT '学分（如 3.0、2.5，支持半学分）',
    `hours`             INT          NOT NULL COMMENT '总学时',
    `teacher_name`      VARCHAR(64)  NOT NULL COMMENT '任课教师姓名（冗余展示；正规做法是 teacher_id 关联教师表）',
    `college`           VARCHAR(64)  NOT NULL COMMENT '开课院系/学院',
    `major`             VARCHAR(64)  DEFAULT NULL COMMENT '开课专业（NULL=不限专业）',
    `campus`            VARCHAR(64)  DEFAULT NULL COMMENT '校区（可空）',
    `exam_type`         VARCHAR(32)  DEFAULT NULL COMMENT '考试形式：考试/考查/论文/机考',
    `language`          VARCHAR(32)  DEFAULT NULL COMMENT '授课语言：中文/英文/双语',
    `term`              VARCHAR(32)  NOT NULL COMMENT '开课学期，如 2026-2027-1',
    `capacity`          INT          NOT NULL COMMENT '选课人数上限（= 总库存，核心！）',
    `selected_count`    INT          NOT NULL DEFAULT 0 COMMENT '已选人数（当前库存，异步落库时 +1）',
    `select_start_time` DATETIME     DEFAULT NULL COMMENT '选课开始时间（时间窗）',
    `select_end_time`   DATETIME     DEFAULT NULL COMMENT '选课结束时间（时间窗）',
    `restrict_grade`    VARCHAR(255) DEFAULT NULL COMMENT '限选年级（逗号分隔，如 2024,2025；NULL=不限）',
    `restrict_major`    VARCHAR(255) DEFAULT NULL COMMENT '限选专业（逗号分隔；NULL=不限）',
    `status`            TINYINT      NOT NULL DEFAULT 0 COMMENT '状态：0=未开放 1=可选 2=已满 3=已结束 4=下架',
    `create_time`       DATETIME     DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    `update_time`       DATETIME     DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    `deleted`           TINYINT      NOT NULL DEFAULT 0 COMMENT '逻辑删除：0=未删 1=已删',
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_course_no` (`course_no`),
    KEY `idx_term_status` (`term`, `status`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='课程信息表';
```

**为什么把「排课时间」和「教室」从主表拆出去**：
- 一门课可能多个时间段（如周一 1-2 节 + 周三 3-4 节），主表塞一个字段存不下；
- 教室其实是「某个时间段」的属性（一门课可能理论在 A 教室、实验在 B 教室），所以放时间段表里。
- 冲突检测需要「星期几 + 第几节」做范围比较，结构化字段才能算，逗号/JSON 字符串没法直接比。

### 3. 选课记录表 `enrollment`

```sql
CREATE TABLE `enrollment` (
    `id`          BIGINT       NOT NULL AUTO_INCREMENT COMMENT '主键',
    `student_id`  BIGINT       NOT NULL COMMENT '学生ID（关联 user.id）',
    `student_no`  VARCHAR(32)  NOT NULL COMMENT '学号（冗余，便于查询）',
    `course_id`   BIGINT       NOT NULL COMMENT '课程ID',
    `course_no`   VARCHAR(32)  NOT NULL COMMENT '课程编号（冗余）',
    `course_name` VARCHAR(128) NOT NULL COMMENT '课程名称（快照，选课时固化）',
    `credit`      DECIMAL(3,1) NOT NULL COMMENT '学分（快照，选课时的学分）',
    `term`        VARCHAR(32)  NOT NULL COMMENT '学期',
    `status`      TINYINT      NOT NULL DEFAULT 0 COMMENT '状态：0=已选 1=已退课 2=已完成 3=已取消(抢课失败回滚)',
    `select_time` DATETIME     DEFAULT CURRENT_TIMESTAMP COMMENT '选课时间',
    `create_time` DATETIME     DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    `update_time` DATETIME     DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    `deleted`     TINYINT      NOT NULL DEFAULT 0 COMMENT '逻辑删除',
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_student_course` (`student_id`, `course_id`),  -- ★ 一人一课的最终兜底
    KEY `idx_student_term` (`student_id`, `term`),
    KEY `idx_course_id` (`course_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='选课记录表';
```

> **`uk_student_course(student_id, course_id)` 是整个抢课防重的根基**，必须先建。后面 MQ 重复投递、并发重复请求，最终都由它挡下。

### 4. Redis key 设计

| key | 类型 | 值 | 用途 |
|-----|------|-----|------|
| `stock:course:{courseId}` | string | 剩余名额 | 课程开放时预加载（= capacity - selected_count），Lua 扣减 |
| `enroll:{studentId}:{courseId}` | string(setnx) | 1 | 幂等键，防同一学生重复抢同一课 |
| `enroll:credits:{studentId}:{term}` | string | 已选学分 | 可选缓存，加速学分上限校验 |

## 三、抢课前置校验（能不能抢）

抢课主流程第一道闸，**顺序有讲究**：越便宜（不查库/不跨网络）的判断越靠前，快速把不合法请求挡掉。

| 顺序 | 校验项 | 依据 | 说明 |
|------|--------|------|------|
| ① | 课程存在且 `status=1`（可选） | Redis 缓存或 DB | 课程不存在/已满/已结束直接拒 |
| ② | 在选课时间窗内 | `select_start_time ~ select_end_time` | 当前时间不在窗口内直接拒 |
| ③ | **幂等防重** | Redis `SETNX enroll:{studentId}:{courseId}` | 同一学生重复抢同一课直接拒（占位成功才继续） |
| ④ | **学分上限** | `已选学分 + 本课学分 ≤ 30` | 查已选课程学分求和 |
| ⑤ | **时间冲突** | 本课时间段 vs 已选课程时间段 | 见下方冲突检测 |
| ⑥ | 限选年级/专业 | `restrict_grade` / `restrict_major` | 可选，有则校验学生是否在限选范围内 |
| ⑦ | 库存充足 | Redis `stock:course:{courseId} > 0` | 真正扣减交给 Lua 原子做（⑦只是粗查，可并入 Lua） |

### 时间冲突检测算法

```
输入：学生已选课程的时间段列表 A，本课程时间段列表 B
冲突 = 存在 a∈A, b∈B 满足：
       a.weekday == b.weekday                     // 同一天
    && a.start_section <= b.end_section           // 节次范围有重叠
    && b.start_section <= a.end_section
    && a.start_week   <= b.end_week               // 周次范围有重叠（可先忽略做简版）
    && b.start_week   <= a.end_week
    && 周次类型兼容（单周/双周，可先忽略）
```

> 简化建议：第一版先只判「同一天 + 节次范围重叠」，忽略周次范围和单双周（这两个是加分项，不是核心）。

### 学分上限计算

```sql
SELECT COALESCE(SUM(credit), 0)
FROM enrollment
WHERE student_id = ? AND term = ? AND status IN (0, 2)  -- 已选 + 已完成
```

判断：`已选学分 + 本课学分 > 30 → 抛 BusinessException("选课学分已满")`。

## 四、抢课主流程（Redis Lua + RabbitMQ）

### 1. 扣减 Redis 库存的 Lua 脚本

> 为什么用 Lua：`查库存` + `扣减` 是两个操作，分开做会有并发窗口（查时还有、扣时没了 → 超卖）。
> Redis 单线程执行 Lua 脚本，整个脚本是**原子**的，天然没有并发问题，**不需要额外加锁**。

```lua
-- KEYS[1] = stock:course:{courseId}
-- 返回：>=0 表示扣减成功后的剩余名额；-1 表示库存不足
local stock = tonumber(redis.call('GET', KEYS[1]))
if not stock or stock <= 0 then
    return -1
end
redis.call('DECR', KEYS[1])
return stock - 1
```

### 2. Service 伪代码（抢课主流程）

```java
public void enroll(Long courseId) {
    Long studentId = UserContext.get().getId();   // 从 ThreadLocal 拿当前登录学生

    // ① 课程存在 + 可选 + 时间窗（可查 Redis 缓存或 DB）
    Course course = getCourse(courseId);
    if (course == null || course.getStatus() != 1) throw new BusinessException("课程不可选");
    if (!inSelectWindow(course)) throw new BusinessException("不在选课时间");

    // ② 幂等防重：setnx 占位，占位失败 = 重复提交
    Boolean first = redisTemplate.opsForValue()
            .setIfAbsent("enroll:" + studentId + ":" + courseId, "1", 10, TimeUnit.MINUTES);
    if (Boolean.FALSE.equals(first)) throw new BusinessException("请勿重复选课");

    try {
        // ③ 学分上限
        BigDecimal used = calcUsedCredits(studentId, course.getTerm());
        if (used.add(course.getCredit()).compareTo(new BigDecimal("30")) > 0)
            throw new BusinessException("选课学分已满");

        // ④ 时间冲突
        if (hasTimeConflict(studentId, courseId, course.getTerm()))
            throw new BusinessException("与已选课程时间冲突");

        // ⑤ Lua 原子扣 Redis 库存
        Long remain = redisTemplate.execute(redisScript, Collections.singletonList("stock:course:" + courseId));
        if (remain == null || remain < 0) throw new BusinessException("课程已抢完");

        // ⑥ 发 MQ 异步落库
        rabbitTemplate.convertAndSend(ENROLL_EXCHANGE, ENROLL_ROUTING_KEY, buildMessage(studentId, course));

    } catch (BusinessException e) {
        // 校验失败要释放幂等占位，否则学生 10 分钟内都抢不了这门课
        redisTemplate.delete("enroll:" + studentId + ":" + courseId);
        throw e;
    }
}
```

> 注意：④⑤ 失败时要删掉 ② 的幂等键，否则「因为学分满被拒」的学生之后也一直被当成重复提交。

### 3. MQ 消费端（异步落库，最终一致）

```java
@RabbitListener(queues = ENROLL_QUEUE)
public void onEnroll(EnrollMessage msg) {
    Long courseId = msg.getCourseId();
    Long studentId = msg.getStudentId();

    // 幂等：唯一索引兜底，重复消费直接跳过
    boolean exists = enrollmentMapper.exists(new LambdaQueryWrapper<Enrollment>()
            .eq(Enrollment::getStudentId, studentId)
            .eq(Enrollment::getCourseId, courseId));
    if (exists) return;

    // ① 条件更新扣库存：UPDATE ... WHERE selected_count < capacity
    //   0 行受影响 = 超卖（Redis 和 MySQL 短暂不一致），回补 Redis 库存并放弃
    int rows = courseMapper.incrSelectedCount(courseId);  // 自定义 SQL：SET selected_count = selected_count + 1 WHERE id=? AND selected_count < capacity
    if (rows == 0) {
        redisTemplate.opsForValue().increment("stock:course:" + courseId);  // 回补
        return;
    }

    // ② 插入选课记录（唯一索引再兜底一次）
    try {
        enrollmentMapper.insert(buildEnrollment(msg));
    } catch (DuplicateKeyException e) {
        // 并发/重复消费撞了唯一索引：扣掉的库存要回补，且这条记录已存在，直接忽略
        courseMapper.decrSelectedCount(courseId);
        redisTemplate.opsForValue().increment("stock:course:" + courseId);
    }
}
```

**三个关键点**：
1. **防超卖双层保险**：Redis Lua `stock <= 0` 拒 + MySQL 条件更新 `WHERE selected_count < capacity` 拒，两头都不会扣成负数。
2. **最终一致**：Redis 先扣（快）、MySQL 后扣（慢），中间短暂不一致。消费失败靠「回补 Redis 库存」补偿。
3. **消费端幂等**：MQ 可能重复投递，靠「先查是否已存在 + 唯一索引捕获 DuplicateKey」保证不重复落库。

## 五、一人一课：并发与防重（捋清「分布式锁」）

### 三个概念别混

| 概念 | 解决的问题 | 本项目对应 | 解法 |
|------|-----------|-----------|------|
| **库存并发扣减** | 多人抢同一份资源互斥 | 多学生抢同一门课 | Lua 原子（不需要锁） |
| **幂等/防重** | 同一请求别执行两次 | 同一学生重复抢同一课 | setnx 幂等键 + DB 唯一索引 |
| **分布式锁** | 跨多步操作的互斥 | （本项目没有） | Redisson 等，用不到 |

### 企业「一人一课」的标准做法（两层）

```
第一层（加速，可选）：Redis setnx 幂等键
    key = enroll:{studentId}:{courseId}     ← 组合 key，不是单 studentId
    作用：快速拦截重复点击，避免打到 DB
    注意：设短 TTL，校验失败要主动释放

第二层（兜底，必须）：数据库唯一索引
    UNIQUE KEY uk_student_course(student_id, course_id)
    作用：无论并发多乱、MQ 重试多少次，DB 里绝无重复记录
```

### 为什么不用「学生 id 做分布式锁」

1. **粒度太粗**：key 只有 studentId，会把这个学生「选 A 课」「选 B 课」全部串行化，白白降低吞吐。
2. **方向反了**：你要防的是「同一学生重复抢同一课」，锁的资源应是 `studentId + courseId`，而不是学生的所有操作。
3. **有更简单的**：防重本质是幂等，setnx 占位 + 唯一索引就够了，真上分布式锁（带续期/释放）反而复杂。

> 结论：**别用「学生 id 分布式锁」，用「组合幂等键 + 唯一索引」**。这才是企业做法，也更好写。

## 六、Elasticsearch 课程搜索

### 1. 索引设计（只存搜索维度，不存实时库存）

```json
{

      "major":       { "type": "text", "analyzer": "ik_max_word" },

      "credit":      { "type": "float" },
      "term":        { "type": "keyword" },
      "status":      { "type": "integer" },
      "language":    { "type": "keyword" }
    }
  }

```

### 2. 数据同步方案（三选一，本项目推荐 ③）

| 方案 | 做法 | 适用 |
|------|------|------|
| ① 双写 | 课程增删改时，同步调 ES 写索引 | 简单，但耦合、可能不一致 |
| ② Canal | 监听 MySQL binlog 自动同步 | 企业级，但引入额外组件 |
| ③ **启动全量导入 + 变更走 MQ 异步刷新** | 启动时把 course 表灌进 ES；增删改后发 MQ 通知刷新 | 本项目推荐，和现有 RabbitMQ 复用 |

### 3. 搜索与库存的边界

```
GET /course/search?keyword=数学
  → ES 搜索（返回课程 id + 元数据）
  → 用 id 列表批量查 Redis stock:course:{id}（实时剩余名额）
  → 拼装返回：元数据 + 剩余名额
```

> ES 里的课程信息是「快照」，库存**永远以 Redis 为准**，ES 不存库存字段。

## 七、分步实现路线（按部就班）

### Step 1：建表 + 实体 + Mapper
- [ ] 执行 `course` / `course_time` / `enrollment` 三张表的 SQL（重点：`uk_student_course` 唯一索引）
- [ ] 新建实体：`entity/Course.java`、`entity/CourseTime.java`、`entity/Enrollment.java`（对齐 User 的 Lombok + `@TableName` + `@TableId` + `@TableLogic` 风格）
- [ ] 新建 Mapper：`CourseMapper`、`CourseTimeMapper`、`EnrollmentMapper`（继承 `BaseMapper`）
- [ ] 自定义 SQL：`CourseMapper.incrSelectedCount`（条件更新扣库存）

### Step 2：课程查询（先 MySQL，后接 ES）
- [ ] `CourseController` + `CourseService`，`GET /course/search?keyword=` 先用 `LambdaQueryWrapper.like` 按课程名/教师查
- [ ] 查询结果补上实时剩余名额（查 Redis `stock:course:{id}`，没有则回源 DB）

### Step 3：抢课前置校验
- [ ] `CourseService.canEnroll(studentId, courseId)`：课程状态、时间窗、幂等、学分上限、时间冲突
- [ ] 写时间冲突检测方法（先简版：同一天 + 节次重叠）

## 八、注意事项（坑）

1. **幂等键要主动释放**：前置校验失败时删掉 setnx 占位，否则学生被「假占用」锁死一段时间。
2. **Redis 和 MySQL 库存最终一致，不是强一致**：Redis 先扣、MySQL 后扣，中间有短暂窗口不一致，靠「回补」兜底；真要强一致得上分布式事务（学习项目不需要）。
3. **消费端必须幂等**：MQ 会重复投递，靠「先查 + 唯一索引捕获 DuplicateKey」。
4. **库存字段别放 ES**：ES 近实时延迟会让库存显示不准，实时库存以 Redis 为准。
5. **学分为小数**：用 `DECIMAL(3,1)` + `BigDecimal`，别用 `float/double`（精度丢）。
6. **`user` 是保留字要加反引号**：`enrollment` 关联 `user.id` 时注意，实体 `@TableName("`user`")` 已处理。
7. **时间冲突的节次边界**：`a.start_section <= b.end_section && b.start_section <= a.end_section` 是「闭区间重叠」判断，别写成相等判断。
