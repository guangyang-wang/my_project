# ES 与 MySQL 双写一致性 —— 简历亮点与面试问答

> 核心亮点：放弃业务代码双写，改用 **Canal 订阅 binlog + RabbitMQ 异步同步**，解决搜索副本（ES）与主库（MySQL）的并发不一致，体现对「最终一致性 / 消息顺序性 / 幂等」的理解。

---

## 一、简历里怎么写

**推荐写法（项目经历下的一条 bullet）：**

> 课程信息同步 Elasticsearch 供中文分词搜索：放弃业务代码双写，改用 **Canal 订阅 MySQL binlog + RabbitMQ 异步同步**，让同一门课程的变更按提交顺序串行落到 ES，从根上消除并发「旧数据覆盖新数据」；配合幂等写入 + 定时对账兜底，实现秒级最终一致。

**空间不够时的精简版：**

> ES 搜索副本同步：Canal 订阅 binlog + MQ 异步同步，靠「binlog 有序 + 主键分区有序消费」解决双写不一致，幂等 + 对账兜底。

## 二、面试官追问 & 怎么答

### Q1：ES 和 MySQL 为什么会双写不一致？
双写是两个独立存储，没有分布式事务串起来，**谁后写谁赢**。并发下：请求 A、B 同时改同一门课，MySQL 靠行锁 + 事务保证了先后顺序，但这个顺序**传导不到 ES**——ES 是无锁、无版本的裸 `save`（按 id 覆盖），谁的网络请求后到谁就覆盖谁。于是出现「MySQL 里是新值、ES 里是旧值」的丢失更新，而且不会再自动纠正。

### Q2：为什么不用业务代码直接双写（先写 MySQL 再写 ES）？
业务代码双写有两个绕不过去的坑：
1. **顺序不可控**：多线程/多实例下，谁先执行 ≠ 谁先提交，消息发出顺序不代表真实业务顺序，并发下照样乱序。
2. **事务窗口**：ES 写在 `@Transactional` 方法内、`commit` 之前，一旦 MySQL 提交失败回滚，ES 里就留下了一条「不存在的课程」。

### Q3：Canal 方案为什么能解决顺序问题？本质是什么？
**本质 = binlog 的有序性 + 按主键分片的局部有序。** binlog 是 MySQL 在数据库层**串行产生**的，同一行的多次变更天然就是事务真实提交的先后顺序——这是「权威真相」。Canal 把「定序」这件事，从不可控的并发应用层，下沉到了天然串行的数据库层。

### Q4：MQ 是全局有序的吗？
**不是，也不需要。** 分布式 MQ 做不到全局有序（跨分区无顺序），也没必要（不同课程之间没有顺序关系）。它做的是**按主键 hash 分片**：同一门课永远进同一个分区/队列，分区内 FIFO 保序。效果就是「不同课程顺序无所谓，同一门课程顺序必须保持」。

### Q5：网络波动会不会导致消息乱序？
**不会，网络波动影响的是「快慢」，不是「先后」。** 顺序靠一条「三环都串行」的链路保证：单生产者串行发送（发 A 确认后才发 B）→ 单分区 FIFO 存储 → 单消费者串行处理。只要三环不并行，前一条重试多少次、多慢，后一条都得等它成功才出发。乱序只会发生在「你打破了串行」的时候（异步并行发送 / 多消费者并发）。

### Q6：RabbitMQ 和 Kafka 怎么选？
看三个维度 + 技术栈：**顺序性**（Kafka 分区 key 天然有序，RabbitMQ 要单队列单消费者自己控）、**堆积能力**（Kafka 落盘设计海量堆积不影响性能，RabbitMQ 堆积上百万会内存告警拖垮 broker）、**吞吐**（Kafka 百万级，RabbitMQ 万级）、**运维**（RabbitMQ 单机即跑最省心）。课程变更量极小 + 技术栈里已有 RabbitMQ → 选 RabbitMQ，按主键分片 + 单消费者串行保证顺序。

### Q7：消费失败 / 消息丢失怎么办？
有序只解决「防乱序」，完整的一致性靠**三件套**：
- **有序**（binlog + 主键分区）→ 防旧盖新；
- **幂等**（ES `save` 按 id upsert 天然幂等）→ 防 MQ 重投重复写；
- **对账兜底**（定时全量/增量重建 + 差异比对）→ 防消息丢失，把最终不一致抹平。

### Q8：逻辑删除怎么处理？
`@TableLogic` 的逻辑删除，`deleteById` 实际执行的是 `UPDATE course SET deleted=1`，所以 **binlog 里是 UPDATE 事件（deleted 0→1），不是 DELETE**。消费端要判断：UPDATE 之后 `deleted=1` → 删 ES 文档，否则课程下架了还能被搜到。

### Q9：为什么接受最终一致，不做强一致？
缓存/搜索副本的正确姿势就是**最终一致**。强一致要上分布式事务（2PC/TCC/SAGA），代价极高且严重拖慢主流程。正确做法是「MySQL 为主、ES 是投影，允许秒级延迟，用对账收敛」，用「有序 + 幂等 + 对账」把不一致窗口控制在秒级、且最终必收敛。

## 三、核心逻辑链（一句话记忆）

**双写不一致（谁后写谁赢）→ 放弃业务双写 → binlog 订阅（有序真相）+ MQ 主键分区（局部有序）+ 串行消费 → 幂等防重 + 对账防丢 → 秒级最终一致。**
