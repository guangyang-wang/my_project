# 排课并发控制 —— 简历亮点与面试问答

> 核心亮点：并发冲突兜底 + 死锁根治 + 方案选型权衡，体现对「数据库索引 / 事务 / 锁」原理的理解。

---

## 一、简历里怎么写

**推荐写法（项目经历下的一条 bullet）：**

> 负责课程排课模块：针对「同一时间片 + 教室」的并发冲突，设计**前置校验 + 联合唯一索引兜底**双层方案保证数据一致性；通过**批量插入排序（锁排序）统一加锁顺序**，从根上消除死锁；权衡后**主动放弃分布式锁**，规避低并发场景的过度设计。

**空间不够时的精简版：**

> 排课并发控制：前置校验 + `(time_slot_id, classroom)` 联合唯一索引兜底防冲突；批量插入锁排序消除死锁；不用分布式锁（低并发过度设计）。

---

## 二、面试官追问 & 怎么答

### Q1：前置校验已经查了冲突，为什么还需要唯一索引？
前置校验是普通 `SELECT`（MVCC 快照读，不加锁），两个线程都能读到「无冲突」再同时插入（check-then-act 竞态），挡不住并发。唯一索引是数据库层最终保证：谁先插入谁成功，后到的报 `DuplicateKeyException`，绝不产生脏数据。前置校验只是「友好提示」，不是并发保证。

### Q2：批量插入为什么会死锁？
多值 `INSERT` 不是一次性拿锁，而是**按 VALUES 顺序逐行加锁**，且事务提交前锁都持有。两个事务插入的时间片**顺序交叉**时（A: [100,101]，B: [101,100]），A 持有 100 等 101，B 持有 101 等 100，形成循环等待 → 死锁。

### Q3：为什么排序能防死锁？
死锁根因是**加锁顺序不一致**。插入前对 timeSlotIds 统一排序，让所有事务按相同顺序竞争锁，就不存在交叉等待，从根上消除死锁（锁排序 / Lock Ordering）。

### Q4：为什么不直接用分布式锁？
排课是管理员低频操作，唯一索引已足够兜底。分布式锁会引入额外复杂度、延迟和运维成本，低并发下是**过度设计**。分布式锁的价值在高并发（如抢课）场景才体现。

### Q5：如果这个接口变高并发（比如抢课），会怎么做？
换成另一套：**Redis 预扣库存（Lua 原子）+ MQ 异步落库 + 唯一索引最终兜底 + 冲突/死锁重试**。排课和抢课是两个量级的问题，方案不同。

### Q6：唯一索引冲突和死锁，哪个该重试？
唯一冲突是「确定失败」（时间教室已被占），重试没用，直接报错；死锁是「暂时失败」（对方事务结束就消失），重试大概率成功。两者分开处理。

### Q7：事务回滚和全局异常处理器怎么配合？
事务**不吞异常**：方法抛异常时先回滚、再把异常继续上抛，全局处理器在 Controller 层接住转成统一 `Result`。前提是方法内不能 try-catch 吞异常——所以 catch `DuplicateKeyException` 后要 **rethrow 成 BusinessException**，既触发回滚又返回友好提示。

## 三、核心逻辑链（一句话记忆）

**问题（并发冲突）→ 前置校验友好提示 + 唯一索引兜底 → 排序消除死锁 → 权衡后放弃分布式锁。**
